 Abstract
Large-scale software specifications challenge direct use by coding agents: the Arkhe OS & AGI —
Integrated Master Document (2nd edition) spans 68,262 lines and 2,287,868 characters — an estimated
570–650 thousand tokens —, exceeding standard 200 thousand-token context windows. This paper turns
that document into an operating manual: the DMCP pipeline (Master-Document-as-Prompt), which slices
the corpus into 50 addressable blocks with stable identifiers, prefixes every prompt with a six-principle
constitution (fail-closed, honest status, block traceability, one phase at a time, executable evidence, and
declared reconciliation of divergent versions), and orders the construction of the arkhe-agi software into
seven phases (F0–F6), from the 15-crate monorepo bootstrap to the MCP server, using executable gates
— cargo check/test/clippy/fmt/deny, the eight gates of the v5 audit, and the governed write-audit-publish
protocol of the aia repository — as acceptance criteria, with logs attached to every commit as evidence.
Universal prompt and audit templates are provided, along with an analysis of limitations (context
saturation, package and API hallucination, internal corpus divergences) and their mitigations. We
conclude that verification, not prompting, is the architecture: block-to-code fidelity is only sustainable
when every specification claim becomes an executable test.
Keywords: prompt engineering; coding agents; spec-driven development; context engineering; fail-closed
verification; ARKHE AGI.

1. Introduction
There is a paradox at the center of every ambitious AI-assisted software project: the most complete
specifications are precisely the ones no language model can read in a single pass. The Arkhe OS & AGI —
Integrated Master Document (2nd edition) is a concrete instance of this paradox. Produced by the auditable
integration of four sources (AGI1, AGI2, AGI3, and AIA), the document packs 68,262 lines and 2,287,868
characters of executable specification — complete monorepos, cryptographic verification pipelines,
ratifiable invariants, training methodologies, and entire Rust repositories (OLIVEIRA, 2026). Converted
into tokens, the corpus occupies, by conservative estimate, between 570 and 650 thousand tokens — a
figure that exceeds the default context window of Claude models (200 thousand tokens) and strains even the
extended one-million-token windows (ANTHROPIC, 2025b; AMAZON WEB SERVICES, 2025). The
question that motivates this tutorial is direct: how can a document of this magnitude be turned into an
operational prompt capable of guiding the complete construction of the arkhe-agi software?
The answer this paper develops and demonstrates is that the Master Document should not be treated as a
monolithic block to be pasted into a conversation field, but rather as a corpus of prompts already structured
for that purpose. The integration that produced the 2nd edition left, as a by-product, a natural slicing
infrastructure: 50 content blocks with stable identifiers (p1-b01 through p6-b06), source line ranges, hashes
of normalized content, a consolidated index of 298 invariant identifiers INV-*, and verification status
markings (VERIFIED, PARTIAL, FAILED, NONEXISTENT) distributed throughout the text
(OLIVEIRA, 2026). Each block is, in essence, an addressable prompt unit — small enough to fit in context,
large enough to describe an entire subsystem. What is missing is not material but method: a flow
architecture that says which block to use, in which order, with which acceptance criterion, and with which
executable evidence.
The literature on code generation with large language models supports this reading. The transition from
prompt engineering to flow engineering, formalized by AlphaCodium, showed that multi-stage pipelines
substantially outperform a single prompt on code problems (RIDNIK et al., 2024). Reference software
agents, such as SWE-agent, demonstrate that the agent–computer interface — not just the model —
determines performance (YANG et al., 2024), while the SWE-bench benchmark shows that frontier models
still fail on most real issues from popular repositories when operating without structure (JIMENEZ et al.,
2024). In parallel, studies on long-context use show that the position of information matters: models tend to
retrieve better what sits at the edges of the window, degrading attention over the middle (LIU et al., 2024).
These three findings converge on the same methodological prescription adopted here: slice, order, and
verify.
This paper thus proposes DMCP — Master-Document-as-Prompt, a seven-phase protocol (F0 through
F6) that transforms the integrated specification into a constructive sequence for the arkhe-agi software, with
four distinctive properties: (i) slicing into stable blocks, inherited from the document's structure; (ii)
constitutional prompting, which fixes the project's fail-closed philosophy as an invariant rule of every
prompt; (iii) verifiable gates, which convert each claim of the specification into an executable test
criterion; and (iv) bidirectional traceability, which ties every generated line of code to the block that
specifies it. The tutorial is written for operators using any contemporary coding agent — the examples
employ Claude Code terminology, but the principles are tool-agnostic (ANTHROPIC, 2025a).
The paper is organized as follows. Section 2 reviews the fundamentals and related work that support the
proposal. Section 3 dissects the anatomy of the Master Document as a corpus of prompts, with metrics and a
mapping of constructive roles. Section 4 formalizes the DMCP pipeline — principles, slicing, context
budget, and phases F0–F6. Section 5 is the tutorial proper, step by step, with reusable prompt templates.
Section 6 confronts counterarguments and limitations, including those documented in the corpus itself.
Section 7 concludes with implications and a future agenda. We adopt the project's own honest-status

2. Fundamentals and related work
2.1 From prompt engineering to flow engineering
The first generation of techniques for steering language models focused on the content of a single prompt:
carefully crafted examples, roles, and instructions. The chain-of-thought technique showed that inducing the
model to produce intermediate reasoning improves performance on complex tasks (WEI et al., 2022), but it
remained confined to a single inference pass. AlphaCodium marked the conceptual turn relevant to this
tutorial: by replacing the single prompt with a test-oriented flow — reflection on the problem,
natural-language reasoning, generation, execution, and iterative correction against public tests —, the
authors substantially raised the hit rate of frontier models on code problems, showing that the process around
the model is the dominant lever (RIDNIK et al., 2024). In operational terms, a 650-thousand-token
specification document was never a prompt: it is a flow-engineering program waiting to be executed.
Two complementary lines consolidate feedback iteration as a quality mechanism. Self-Refine shows that
models can refine their own outputs when given structured feedback — including self-generated feedback
— across multiple iterations (MADAAN et al., 2023). Reflexion adds verbal memory of failures: the agent
summarizes why the previous attempt failed and condenses that learning into the next attempt, without
weight updates (SHINN et al., 2023). Both mechanisms are incorporated into DMCP in two concrete forms:
the executable-gate loop (which returns error logs as objective feedback) and the phase-audit prompt
(Section 5.9), which produces verbal failure syntheses to feed the next phase.
2.2 Coding agents: raw capability is not enough
The evaluation of agents in software engineering tempers optimism with evidence. SWE-bench proposes the
task most faithful to reality — resolving real issues from popular repositories — and concluded, in its
original formulation, that both frontier proprietary models and fine-tuned variants resolved only the simplest
issues (JIMENEZ et al., 2024). SWE-agent attributes a relevant share of performance to the agent–computer
interface: terminals, editors, and commands designed for the agent yield efficacy jumps comparable to
model changes (YANG et al., 2024). The lesson for this tutorial is twofold: first, the structure of the target
repository and of the input materials must be designed for the agent; second, each construction phase needs
executable acceptance criteria, since self-confidence is not a reliable attribute of these systems.
The Claude Code practice documentation adds the context-budget dimension. The official guide
recommends planning before implementing, verifying every change with tests, and — crucially — treating
the context window as a resource that degrades: as it fills up, performance drops, and long debugging
sessions consume tens of thousands of tokens (ANTHROPIC, 2025a). Context engineering formalizes this
concern: the right artifact in the right context, with history compaction, on-demand retrieval, and delegation
to subagents, instead of indiscriminate accumulation of material (ANTHROPIC, 2025b). These precepts of
industrial practice coincide point by point with the academic findings on context position and saturation and
justify the strict per-prompt budget adopted in Section 4.3.

2.3 Specification as contract: spec-driven development
In September 2025, GitHub institutionalized spec-driven development with Spec Kit, a set of tools and
standardized phases — constitution, specification, clarify, plan, tasks, analyze, and implement — in which
the specification precedes and constrains code generation by agents (GITHUB, 2025). The thesis of the
movement is that the specification is the program: code becomes derived, and fidelity to the specification
becomes the primary metric. The Arkhe Master Document occupies an extreme position on this spectrum:
instead of a synthetic specification drafted to guide an agent, it is an organic specification, accumulated
through the integration of four sources, which already contains complete code, audit corrections, and
acceptance criteria. DMCP can be read as the adaptation of the Spec Kit cycle to a pre-existing large-scale
corpus: the constitution and specification phases have already been fulfilled by the document; what remains
is slicing, planning, tasks, and implementation — which is exactly the structure of Sections 4 and 5.
2.4 Long context and retrieval: why pasting everything is not enough
Retrieval-augmented generation (RAG) established that retrieving relevant passages on demand
outperforms parametric memorization for knowledge-intensive tasks (LEWIS et al., 2020). For code,
RepoCoder refined the idea to the repository level: iterative retrieval, in which the generated sketch guides
the next search for relevant context, improves multi-file code completeness (ZHANG et al., 2023). Position
evidence completes the picture: Liu et al. show that multi-document models exhibit U-shaped performance
— high at the edges of the context, degraded in the middle — and that performance degrades as the number
of relevant documents grows, even when the window is sufficient (LIU et al., 2024). Even though
one-million-token windows numerically accommodate the Master Document (AMAZON WEB
SERVICES, 2025; GOOGLE, 2026), the model's cognitive economy does not keep pace with storage
economy: pasting 650 thousand tokens is, in light of these results, a worst-case strategy. The methodological
consequence is the slicing-and-retrieval hierarchy detailed in Section 4.3.
2.5 Known risks: API and package hallucination
The risk specific to model-generated code is well documented. Spracklen et al. systematically analyze
package hallucination — models recommending libraries that do not exist — and show that the
phenomenon is widespread, persists in commercial models, and opens a supply-chain attack surface,
slopsquatting, in which third parties register the hallucinated packages (SPRACKLEN et al., 2025). The
notable detail, for the purposes of this tutorial, is that the Master Document itself records the API-level
analogue: the missing-contract analysis of the aia repository (Block 6.5) documents calls to functions that
do not exist in the v1 implementation — ghost APIs — and the static analyses of arkhe-aegis (Block 6.4)
catalog 21 fixes (C1–C7, A1–A8, R1–R5), including length-prefixed hashing for the INV-AEGIS-04
invariant and timeouts to eliminate a fail-hang (OLIVEIRA, 2026). The corpus, in other words, already
contains its own case study of code-generation failure — and the tutorial will appropriate it as evidence that
executable gates are not an accessory but a requirement.

3. Anatomy of the Master Document as a prompt corpus
3.1 Corpus metrics
Before slicing, one must measure. Table 1 consolidates the objective metrics of the source corpus,
computed over the canonical 2nd-edition file with its registered SHA-256 hash. The document is large —
roughly 255 thousand words and an estimated 570 to 650 thousand tokens, assuming the usual ratio of 3.5 to
4 characters per token for technical Portuguese mixed with code — but it is large in a structured way: the
integration kept the full-preservation policy (zero deletion of unique content), kept divergent versions in
parallel with explanatory notes, and merged only exact duplicates, flagged with ♻ warnings that point to the
preserved copy (OLIVEIRA, 2026). This editorial discipline is what makes slicing safe: every block has

3.2 The six parts and their constructive roles
The thematic map of the document (Section 0.3) organizes content by subject, but software construction
requires a cut by constructive role: what each part supplies to the generation pipeline. Table 2 presents this
mapping. Two observations deserve emphasis. First: Part IV — complementary research for a balance of

3.3 Blocks as prompt units
The stable identifier of each block — p<part>-b<no> — is the protocol's fundamental address. Each anchor
corresponds to an independent document from the original sources, with a source line range (for instance,
block 2.6, Arkhe AGI — Complete, Corrected, and Verified Monorepo, spans lines 9,073–14,895 of
AGI1.txt) and a hash of normalized content registered in the traceability map of Part V.3 (OLIVEIRA,
2026). The largest content block, 2.6, has 5,823 lines — somewhere between 25 and 35 thousand tokens,
comfortably inside a context budget of 60 thousand tokens per prompt when combined only with the
constitution and a repository summary. This fit property is not accidental: it enables DMCP's most
important operating rule — one block per prompt, one goal per block —, which keeps the middle of the
context free for the material that really matters and circumvents the documented positional degradation
(LIU et al., 2024).
The blocks also solve, by construction, the problem of verifiable citation in prompts. Instead of instructing
the agent with loose paraphrases — fertile ground for hallucination —, each prompt cites the source block
and, where pertinent, the identifier of the invariant (INV-*) whose violation must be prevented. The
consolidated index of Part V.2, with its 298 identifiers grouped by domain (INV-CORE, INV-CLAIM,
INV-TRAIN, INV-AEGIS, among 45 other groups), works as the index of acceptance criteria (OLIVEIRA,
2026). The result is a chain of custody: block → prompt → generated code → gate → evidence → commit,
with every link pointing to the previous one.

3.4 Honest status and gates as acceptance criteria
The most valuable methodological feature of the corpus is not technical but epistemic: the honest-status
policy. Components and claims carry explicit markings — VERIFIED, PARTIAL, FAILED,
NONEXISTENT —, and the corpus itself acknowledges that the material is, mostly, executable
specification and skeletons, and that Arkhe OS is not an AGI but the verification infrastructure on which a
verifiable AGI could be built and audited (OLIVEIRA, 2026). For a generation pipeline, this means every
prompt inherits an honesty contract: the agent must not promise what it has not executed. The project's
fail-closed philosophy — when in doubt, reject; capabilities are machine-checkable declarations —
becomes the pipeline's progress rule: a phase completes only when its gates execute and pass, and the first
piece of evidence of any phase is the log of the verification command.
Three gate families in the corpus structure that rule. The core family, consolidated by the v5 audit, runs
eight gates in run-all-gates.sh: corrected bimodality, Invariant deserialization, Claim round-trip,
regenerated trybuild, cargo test --workspace, cargo clippy, cargo fmt, and cargo deny (with the
CVE-2026-22696 advisory) (OLIVEIRA, 2026, Block 2.1). The artifact verification pipeline family defines
the path Gate 0 (sanitization) → Gate 0.5 ("Jev" classification) → Gate 1 (BLAKE3 hash) → Gate 2 (hybrid
Ed25519 + ML-DSA signature) → Gate 3 (MMR inclusion), extended to a Gate 4 for intellectual property
in Arkhe IP. The governed-data family, in the aia repository, enforces the governed WAP protocol
(write-audit-publish): no operation touches the main branch without AEGIS authorization, verification, and
audit, with record_hash per operation and 14 ratifiable invariants (OLIVEIRA, 2026, Part VI). In DMCP,
these families become the acceptance criteria of phases F1, F2, and F3, respectively.
4. Methodology: the Master-Document-as-Prompt pipeline (DMCP)
4.1 Cycle overview
DMCP organizes the construction of arkhe-agi into seven sequential phases (F0–F6), each fed by specific
blocks of the Master Document and closed by an executable verification gate. The elementary cycle of each
phase has five moments: (1) extraction of the source block from the canonical corpus, by stable identifier;
(2) contextualization, through injection of the constitutional prompt and a summary of the repository's
current state; (3) generation of the phase's code or artifacts by the coding agent; (4) verification, through
gate execution with log collection as evidence; and (5) integration, through a commit atomically associated
with the evidence and with the block that specifies the change. Figure 1 shows the sequence and the
feedback mechanism: when a gate fails, the audit prompt (Section 5.9) synthesizes the failure in verbal
language — in the spirit of Reflexion (SHINN et al., 2023) — and the phase is re-executed with the new
material, without abandoning the disciplined context budget.

This architecture is deliberately flow engineering in the AlphaCodium sense (RIDNIK et al., 2024), not
prompt engineering: the value lies in the sequence, in the pass criteria between stages, and in the
accumulated evidence, not in the perfect wording of a single instruction. It is also compatible with the Spec
Kit specification cycle (GITHUB, 2025), with one founding inversion: instead of writing the specification
and then implementing it, DMCP starts from a specification that already exists — inherited, large, partially
inconsistent — and concentrates all methodological effort on slicing it, reconciling it, and verifying it.
4.2 Constitutional principles of the prompt
Every prompt emitted by DMCP carries a fixed constitutional prefix — an invariant block of rules that
encodes the project's philosophy. This technique is current practice in coding agents, where files such as
CLAUDE.md or AGENTS.md serve as the repository's persistent rule memory (ANTHROPIC, 2025a). Six
principles form the core: P1 — fail-closed: when in doubt, reject; no attempt to "make it work" at the
expense of verification. P2 — honest status: the agent declares what it executed and what it did not;
skeletons remain marked as skeletons. P3 — block traceability: every code change cites the source block
(p*-b**) and, when applicable, the invariant (INV-*). P4 — one phase at a time: no prompt advances
phases; scope creep is a violation, not initiative. P5 — executable evidence: claims of working behavior
require a log; "prove, do not promise". P6 — declared reconciliation: when facing divergent versions of
the corpus, the agent does not choose silently; it applies the precedence rule declared in the prompt (v0.2.0
over v0.1.0; aia v2 over v1; merged ♻ duplicates read once) and records the decision.
Principles P2 and P6 deserve additional justification, because they derive from internal findings of the
corpus rather than from generic good practice. P2 inherits the document's honest-status policy — which
marks components as PARTIAL or FAILED and acknowledges the skeleton nature of a substantial part of
the monorepo (OLIVEIRA, 2026) — and turns it into agent discipline: without it, generation tends to
"complete" stubs with plausible, unverified implementations — exactly the class of error the aia audit
documented as ghost APIs (Block 6.5). P6 exists because the corpus deliberately keeps divergent versions in
parallel: OS Layer v0.1.0 (Block 2.14) and the post-fix v0.2.0 (Block 3.28); the aia repository v1 (Block
6.1) and v2 (Block 6.2), with structural similarity of about 26.9%. Without an explicit precedence rule, the
agent mixes interfaces from the two versions — a failure mode that the missing-contract analysis
demonstrates to be real, not hypothetical (OLIVEIRA, 2026).

4.5 The verification loop as the progress criterion
Progress in DMCP is defined operationally: a phase advances when its gates pass and the evidence is
attached to the commit; a phase does not advance because it looks plausible. This criterion is the direct
transposition of the corpus's machine-checkable principle — capabilities are proven, not promised
(OLIVEIRA, 2026) — and of the agent-evaluation findings, in which external verification, not model
confidence, is the reliable predictor of correctness (JIMENEZ et al., 2024). In practice, the loop has three
possible outcomes per iteration: (i) green: gates pass; evidence attached; next phase; (ii) red with known
cause: the log points to a specific failure; correction prompt with the log excerpt + the target section of the
relevant block (8–15k tokens); (iii) red with obscure cause: the audit prompt synthesizes the failure
verbally (Reflexion), and the phase re-runs with the synthesis included (SHINN et al., 2023). The
recommended limit is three feedback iterations per gate; if the failure persists, the phase must be split — a
sign that the prompt carried too much scope, violating P4.

This section is the operational manual of DMCP. We assume an empty arkhe-agi repository, the canonical

Claude Code nomenclature, in which CLAUDE.md carries persistent rules and sessions can be driven by
written prompts (ANTHROPIC, 2025a). The numbering of the steps corresponds to phases F0–F6,
preceded by two preparation steps (0A and 0B).
5.1 Step 0A — Environment setup and the repository constitution
Prepare the host environment: a stable Rust toolchain (rustup), cargo-deny and cargo-audit (for the
dependency and CVE gates), Python 3.11+ (SSMDP testbed and utilities), Node.js 20+ (frontend and
MCP), and, for phase F5, the Lean 4 and TLA+ executables corresponding to the Part I blocks. Next, write
the repository constitution — the CLAUDE.md/AGENTS.md file that every prompt will inherit. Listing 1
presents a minimal template, derived from the principles of Section 4.2 and from the document's own text
(OLIVEIRA, 2026). The practical effect of this constitution is to turn the fail-closed philosophy into a local
constraint of the agent: it cannot mark as complete what it has not executed, nor import wrong corpus
versions without declaring the precedence.

5.2 Step 0B — Slicing the corpus into addressable prompts
Generate, once and for all, the prompt index: a docs/dmcp/blocks/ directory with one Markdown file per
corpus block, named by the stable identifier (p1-b01.md … p6-b06.md), plus two derived indexes —
invariants.md (extraction of the 298 INV-* with their first occurrence, mirroring Part V.2) and phases.md
(Table 4 of the tutorial). Listing 2 provides the slicing script, which exploits the document's HTML anchors
(<a id='p2-b05'></a>) as block boundaries. The cost of the procedure is minimal and the benefit is
structural: from here on, every prompt is issued by address (p2-b06), never by manual navigation of the full
document.
Listing 2 – Slicing the Master Document into addressable blocks (Python).
#!/usr/bin/env python3
# Slice the master document into stable prompt-addressable blocks.
import re, pathlib, hashlib
SRC = pathlib.Path("docs/master-integrated-ed2.md")
DST = pathlib.Path("docs/dmcp/blocks"); DST.mkdir(parents=True, exist_ok=True)
text = SRC.read_text(encoding="utf-8")
# block anchors: <a id="p1-b01"></a> ... <a id="p6-b06"></a>
pat = re.compile(r'^<a id="(p\d-b\d+)"></a>\s*$', re.M)
marks = [(m.group(1), m.start()) for m in pat.finditer(text)]
marks.append(("EOF", len(text)))
manifest = []
for (bid, start), (_, end) in zip(marks, marks[1:]):
    chunk = text[start:end]
    out = DST / f"{bid}.md"
    out.write_text(chunk, encoding="utf-8")
    sha16 = hashlib.sha256(chunk.encode()).hexdigest()[:16]
    manifest.append(f"{bid},{out.name},{chunk.count(chr(10))},{sha16}")
pathlib.Path("docs/dmcp/manifest.csv").write_text("\n".join(manifest), encoding="utf-8")
print(f"{len(manifest)} blocks extracted -> {DST}")

6. Counterarguments and limitations
6.1 One-million-token windows do not solve the problem
The first counterargument is the most obvious: if one-million-token context windows exist (AMAZON
WEB SERVICES, 2025; GOOGLE, 2026), why not simply paste the whole Master Document? The
empirical answer comes from the position and saturation evidence: the U-shaped performance documented
by Liu et al. indicates that the middle of long contexts is where information gets lost, and performance
degrades as distractor material grows, even when the window numerically fits (LIU et al., 2024). The
engineering answer reinforces the first: expensive context is slow, costly context, and industrial agent
practice recommends precisely the opposite — load what is necessary and retrieve the rest on demand
(ANTHROPIC, 2025b). There is also a practical limit the tutorial cannot abstract away: long iterations
consume additional context with every file read and command execution, so even the disciplined strategy
needs history compaction in long sessions. DMCP mitigates — it does not eliminate — this limitation, and it
is honest about it: large phases still require multiple sessions with state persisted in the repository (commits,
logs, manifests), not in the conversation.
6.2 The specification is not truth: unverified claims inside the corpus
The second counterargument comes from inside the corpus itself. Part IV of the document — the
complementary research track — records that not everything the specification claims could be verified: the
did:cid identity method was not located in the W3C/DIF registries; the reference "arXiv:2605.28405" does
not exist — the real DeepMind framework is "Levels of AGI", arXiv:2311.02462, as Part IV itself records;
and "Cluster-Aware Upcycling (CVPR 2026)" remains not located (OLIVEIRA, 2026). For the DMCP
operator, the consequence is a hygiene rule: prompts cite blocks and executable criteria, never isolated
out-of-context claims; and every corpus claim marked as unverified must be treated as a hypothesis to test,
not as a requirement. The tutorial inherits the Part IV balance table as an initial "suspect list" — the
alternative, filtering or "fixing" the corpus, would violate the full-preservation policy that gives the
document its auditable utility.
6.3 Implementation hallucination: the empirical case of ghost APIs
The third counterargument is the most technical: even with a perfect specification and disciplined context,
the agent hallucinates — APIs that do not exist, nonexistent packages, incompatible contracts. The literature
confirms the generality of the phenomenon (SPRACKLEN et al., 2025), and the corpus offers the API-level
analogue: the analysis of the aia repository documents calls to functions that do not exist in the v1
implementation — ghost APIs —, fixed only in v2 after the static analyses (OLIVEIRA, 2026, Blocks
6.4–6.5). DMCP's mitigations are three, and none suffices alone: executable gates (the log rejects code that
does not run), dependency verification before introduction (cargo search/cargo add;
cargo-deny/cargo-vet in the gates), and the block-citation rule (P3), which reduces — but does not
eliminate — the space of free paraphrases in which hallucination flourishes. The residual risk is accepted
and declared: the tutorial does not guarantee the absence of hallucination; it guarantees that hallucination
does not cross a gate without being recorded as failure evidence.

6.4 Internal divergences of the corpus and the cost of reconciliation
A skeptic would point out, rightly, that the corpus keeps divergent versions in parallel — OS Layer v0.1.0
versus v0.2.0, aia v1 versus v2, plus three merged duplicates — and that this transfers the reconciliation
burden to the operator. It is a real burden, and P6 exists to make it manageable: declared precedence,
recorded decision, no silent choices. But it is fair to acknowledge the mechanism's limit: version-based
precedence resolves conflicts between versions, not conflicts within the same version — for instance,
between the crate template of Block 2.6 and the completeness seal of Block 6.6, which belong to distinct
iterations of the monorepo. In those cases, DMCP prescribes human escalation (the ESCALATE outcome
of the audit prompt, Listing 4), because the decision involves editorial judgment about the specification that
no executable gate captures. The total cost of reconciliation is therefore non-zero and heterogeneous,
concentrated in phases F0 and F3.
6.5 Wishful scope: what the tutorial deliberately does not promise
The fifth counterargument is the most fundamental: the specification describes, among other things, a
Global South AGI with federated training on distributed accelerators, and no prompt protocol builds an
AGI. The tutorial does not dispute that point — it disputes the scope. The product of DMCP is the
verifiable arkhe-agi monorepo: a compilable foundation with green gates, ratifiable governance, governed
data with WAP, cognition crates implemented on that foundation, and the training pipeline as attestation
code — not the training of a foundation model, which is a material operation dependent on external
infrastructure. This restriction is not evasive; it is the same as the corpus's, which acknowledges being
mostly executable specification and skeletons and that Arkhe OS is not an AGI but the verification
infrastructure on which a verifiable AGI could be built and audited (OLIVEIRA, 2026). The tutorial applies
to its own outcome the honest-status discipline it asks of the agent.
6.6 Risk and mitigation synthesis
Table 5 consolidates the risks discussed in this section and their mitigations, as a quick reference for the
operator. No row of the table is optional: the experience documented in the corpus itself — ghost APIs
fixed, gates added, versions reconciled — is the proof that the verification regime is not ceremony but the
mechanism that turns a wishful specification into a built system. The reader may note that all mitigations are
procedural or executable; none depends on trust in the model, and that is, in our assessment, the tutorial's
central lesson.

7. Conclusion and implications
This tutorial started from a practical question — how to use a 68,262-line specification document as a
prompt for the complete construction of a software system — and answered with an operational protocol,
DMCP, which slices the ARKHE OS & AGI Master Document into 50 addressable blocks, prefixes every
prompt with a six-principle constitution derived from the project's fail-closed philosophy, orders
construction into seven phases (F0–F6) with executable gates as acceptance criteria, and closes every cycle
with evidence attached to the commit. The methodological defense of the protocol does not rest on
optimism about language models but on the opposite set of evidence: attention degradation in long contexts
(LIU et al., 2024), package and API hallucination (SPRACKLEN et al., 2025), the modest performance of
structureless agents (JIMENEZ et al., 2024) — and, decisively, the corpus's own internal case study, whose
audit of the aia repository documented and fixed 21 generated-implementation defects. DMCP is the
formalization of a lesson the corpus already contained: in fail-closed systems, verification is the
architecture.
The implications go beyond the project treated here. For projects with inherited large-scale specifications
— corporate legacy, technical standards, accumulated design documents —, the tutorial shows that the
slicing infrastructure (stable anchors, hashes, criteria indexes) is the asset that turns documentation into a
constructive program; without it, the document is merely big. For spec-driven development practice with
agents (GITHUB, 2025), DMCP adds the declared-precedence pattern for divergent versions of the
specification, a problem that emerges naturally when the specification is organic and versioned in parallel.
And for research on coding agents, the Arkhe case suggests an evaluation metric complementary to
SWE-bench: construction fidelity to an adversarial specification — large, divergent, and partially
unverifiable — measured by executable gates and block-to-code traceability.
Future work follows three fronts. The first is execution: running the F0–F3 pipeline end to end with
contemporary agents, publishing the gate logs as a public replication artifact — the same evidence standard
the corpus demands of its own components. The second is orchestrator automation: converting Table 4 and
the templates of Listings 3–4 into a runner that issues prompts, executes gates, and maintains the
block-commit traceability manifest without manual intervention per iteration. The third is the formal
verification of the governance properties (quorum, timelock, WAP) in TLA+, closing the loop between the
written specification and the executable guarantee. Until then, the operator has the essentials: a map, a
constitution, and a progress rule — prove, do not promise.
