Abstract
Open-weight machine-learning artifacts circulate through distribution chains characterized by opaque provenance,
executable metadata, and trust delegated to promises. This article consolidates and extends arkhe.gguf, the
model-verification component of the Arkhe OS trust layer, tracking its evolution from a delegation package
(schema v1.2) to a complete project structure (schema v1.3). The framework's methodological axiom — what
does not exist is not simulated; it is specified — separates generated artifacts (a byte-exact 24-byte GGUF v3
header fixture whose SHA-256 digest we compute by deterministic execution), delegated execution steps, and
explicitly non-generable items. The technical contribution is a fail-closed, four-gate verification pipeline: Gate 0
sanitizes GGUF metadata against two verified parser vulnerabilities (CVE-2026-65315, Ollama;
CVE-2025-53630, llama.cpp); Gate 1 verifies dual SHA-256/BLAKE3 digests; Gate 2 verifies keyless Sigstore
signatures over an in-toto Statement v1 manifest; Gate 3 verifies RFC 6962 inclusion and consistency proofs plus
a witness quorum of at least two checkpoint cosignatures. Schema v1.3 adds a source block for pre-extension
hashes, an external-manifest hash location, CVE attestation fields, and Safenet-enforced revocation. We further
document an honest-delegation methodology, a thirteen-step provenance checklist, tooling errata discovered
during verification (rekor-cli flag mismatches), and negative tests that make fail-closed behavior an executable
specification. We conclude that attestation constitutes an epistemically honest floor — signed is not safe, identity
is not behavior — and outline the path from PROMISE to VERIFIED within a complete digital-sovereignty stack.
Keywords: model provenance; GGUF; cryptographic attestation; Sigstore; transparency log; witness quorum; AI
supply-chain security; fail-closed verification.

1. Introduction
On February 21, 2025, the exchange Bybit lost approximately US$1.5 billion to North Korean actors
whom the FBI attributes to TraderTraitor [28], [29] — the largest cryptocurrency theft recorded to date.
The detail that matters here is not the magnitude but the mechanism: the cryptography worked
flawlessly, and what was compromised was the signing interface, which led operators to approve
transactions whose real semantics differed from what they believed they were approving. The distance
between what one believes one is signing and what one actually verifies is the same epistemic void that
currently crosses the machine-learning model supply chain, in which billions of bytes of weights change
hands daily with no requirement of cryptographic evidence attached to the artifact itself.
In the open-model ecosystem, that void has already produced concrete incidents. JFrog documented
models hosted on Hugging Face that silently execute arbitrary code during deserialization via crafted
pickle payloads [5]; a subsequent scan concentrated roughly one hundred malicious models on the
platform [6], [7]. In February 2025, the nullifAI campaign used malformed pickle files to bypass
automated scanners [8], and the scanning tool itself was later shown to be bypassable (CVE-2025-1716)
[9]. The technical root is documented in the Python standard library itself: pickle data can execute
arbitrary code during deserialization and must never be unpickled from untrusted sources [3]. The
safetensors format [4] eliminated the code-execution attack class — but a safe format is not provenance:
intact bytes do not answer who produced the model, when, with what identity, under which capability
declarations, and with what distribution history.
Meanwhile the parser layer — the code that reads model containers — accumulated its own
vulnerability record. Between 2024 and 2026, llama.cpp and Ollama, the two most widely deployed
local inference runtimes, disclosed heap overflows, integer overflows, and uncontrolled memory
allocations in GGUF metadata parsing (CVE-2024-23496, CVE-2024-23605, CVE-2024-37032,
CVE-2024-39719 through CVE-2024-39721, CVE-2025-53630, and CVE-2026-65315) [10], [11], [12],
[13], [14], [15]. A model file is thus not merely data: it is a parser input with a demonstrated history of
memory-corruption consequences, and its metadata block is an attack surface long before the first token
is generated.
This article takes as its object of study the arkhe.gguf framework — the model- verification component
of the Arkhe OS trust layer [36] — across its two most recent source documents: the consolidated
delegation package (seal ARKHE-GGUF-DELEGATION-CONSOLIDATED-2026-09-15) and the
complete project structure (seal ARKHE-GGUF-COMPLETE-STRUCTURE-2026-09-15), both dated
September 15, 2026. The package is an engineering document with an explicit methodological thesis,
summarized in its golden rule: when evidence does not exist, it is not simulated; what cannot be
generated is specified. Hashes that have not been computed appear as <CALCULATE> placeholders;
capabilities that have not been verified are declared as an empty list; weights, base models, trust roots,
and signatures that require external execution resources are enumerated as non-generable items rather
than fabricated.
Our contribution is fourfold. First, we dissect the framework's two-layer construction: a delegation
methodology that separates the generable from the executable and the declarable (Section 3), and an
attestation schema that reached version 1.3 with five blocks and an expanded rule set (Section 4).
Second, we formalize the fail-closed four-gate verification pipeline now implemented as a Rust
workspace — sanitization, hash, signature, and transparency-log verification with witness quorum —

2. Background and Threat Model
2.1 The GGUF format
GGUF (GGML Universal File) is the container format used by llama.cpp, Ollama, and the broade
local-inference ecosystem to distribute quantized language models [1]. Its v3 header is deliberately
compact: a four-byte magic (the ASCII bytes GGUF), a little- endian uint32 version, a uint64 tensor
count, and a uint64 metadata key-value count, followed by the metadata block and tensor data [1], [2].
The metadata block is an ordered map whose values are typed (uints, floats, booleans, strings, arrays);
the format prescribes a default alignment of 32 bytes unless the general.alignment key states otherwise
[1]. Hugging Face Hub treats GGUF as a first-class distribution format [2], which makes the header and
its metadata the first code path every local runtime executes when loading a model from public
infrastructure. This is precisely the surface that arkhe.gguf targets: the framework treats the header as a
verification object, injects its own attestation keys into the metadata namespace, and insists that any
consumer parse it only after sanitization.

2.3 The provenance gap and related infrastructure
Format safety and parser hygiene address integrity of execution, not authenticity of origin. The
provenance gap has a mature institutional response in the software supply chain, and arkhe.gguf
deliberately reuses it rather than inventing new cryptography. Sigstore provides keyless signing in which
an OIDC identity (for CI, the GitHub Actions issuer token.actions.githubusercontent.com) is bound into
a short-lived Fulcio certificate, with signature objects recorded in the Rekor transparency log [16], [19],
[20], [40]. Certificate Transparency contributed the underlying append-only machinery: RFC 6962 defines
Merkle inclusion and consistency proofs [17], later consolidated in RFC 9162 [18], and the structure
descends from Merkle's original signature scheme [25]. SLSA contributes build-level provenance
vocabulary [23], and in-toto contributes the Statement v1 envelope whose subject digests enumerate
exactly which files a signature covers [22]. On the model side, the OpenSSF Model Signing tool
(model-transparency; PyPI package model-signing) wraps these primitives for ML artifacts [21], and the
Model Cards literature supplies the declaration vocabulary that the schema's capability fields
operationalize [24]. Hash agility is provided by dual SHA-256/BLAKE3 digests [26], [27]. What was
missing, and what arkhe.gguf specifies, is the binding of this machinery to the specific container format,
metadata namespace, and parser threat model of GGUF — plus the honesty discipline that keeps
declaration separate from verification.

3. Methodology: Specify, Don't Simulate
3.1 The delegation-package pattern
The arkhe.gguf documents practice a methodology that deserves explicit treatment because it is unusual
in AI engineering writing. A delegation package is neither a specification frozen in intent nor a
fabricated demonstration; it is a three-way ledger. The generable is generated: twelve artifacts in the
consolidated package, growing to more than twenty-five in the complete project structure — fixture,
schemas, scripts, Rust crates, configuration, documentation, and negative tests. The executable is
delegated: thirteen steps that require real resources (model downloads, OIDC identities, log
submissions) are written as a checklist with acceptance criteria, expected exit codes, and prohibitions.
The non-generable is declared: training weights, the base model, a real trust root, a real Rekor inclusion
proof, a real Sigstore signature, and the resulting production arkhe.gguf itself are listed in a
what-was-not-generated table [36]. Every hash that could not be computed appears as the literal
placeholder <CALCULATE>.
The pattern's value is epistemic. A reader can distinguish, at every point in the document, between
claims that are specifications (auditable against external references), claims that are artifacts (auditable
by re-execution), and claims that are future obligations (auditable against the acceptance criteria). We
note one internal inconsistency that the methodology itself surfaces: the opening ledger of the
consolidated package counts five non-generable items while its closing README table counts six (the
production arkhe.gguf appears only in the latter) — exactly the kind of discrepancy that consistency
checks in Section 4.3 are designed to catch, and exactly the kind that a simulated package would have
hidden.
3.2 The byte-exact fixture and the computed digest
The framework's minimal verifiable artifact is a 24-byte GGUF v3 header with zero tensors and zero
metadata pairs (Figure 1, Listing 1). Its bytes are fully determined by the format specification: magic
GGUF, version 3, and two zero counts in little- endian encoding [1]. Because the bytes are deterministic,
the fixture functions as a cross-implementation test vector: the Python generator, the Rust parser tests,
and any third-party reimplementation must agree on both the bytes and their digests. In preparing this
article we executed the digest computation locally and obtained SHA-256
a4e5e156ddec27e286f75328784d7106b60a4eb1d246e950a001a3f944fbda99 over the hex string
474755460300000000000000000000000000000000000000 — the same value reported in the source
package, which had itself computed it by execution rather than asserting it. BLAKE3, by contrast,
remained a placeholder in our environment because the reference implementation was not installable
offline; the package's discipline is that the placeholder stays visibly unfilled, marking an obligation,
rather than being invented [27].

3.3 Fail-closed as a design axiom
Across all four gates, the package specifies a single failure semantics: fail-closed. Any gate that cannot
complete its verification rejects the artifact; there is no degraded mode, no warning-only path, and no
default-allow branch. The choice is deliberately conservative and is justified by the incident record of
Section 2: warning-path security is precisely the failure mode that turned interface approval into a
US$1.5 billion loss at Bybit [28], [31]. What makes the axiom more than rhetoric is Section 5.4: the
package ships negative tests whose success condition is that malformed inputs are rejected, so the
fail-closed property is itself executable and regressable, not merely asserted.
4. The Attestation Schema v1.3
4.1 Five blocks
Schema version 1.3 organizes an attestation into five top-level blocks under the arkhe.attestation.*
namespace (Figure 2). The source block (new in v1.3) records the SHA-256 and BLAKE3 digests and
the size of the base artifact before metadata extension. The verifiable block records signing time, the
Ed25519 signature algorithm, the signing identity (OIDC subject, identity provider, Fulcio issuer), the
sanitization flag, the CVE list checked, and the model-signing manifest summary. The anchored block
carries the transparency-log evidence: anchor type rekor, log identifier and index, UUID, tree size, root
hash, inclusion proof, and — new in v1.3 — a consistency proof and witness quorum with cosignatures.
The attested block carries the declaration: type PROMISE, an explicitly empty declared-capabilities list,
an explicit not-capabilities list (code-execution, network-access, file-write, shell-execution), an SLSA
level of 0 flagged as undefined, the signer trust root, and the disclaimer that capabilities are signer
claims, not verifications [24], [36]. The revocation block points to a revocation document and names the
revocation strategies, which v1.3 extends from short_lived alone to short_lived plus safenet_enforced.

4.2 What changed from v1.2 to v1.3
The delta from v1.2 to v1.3 is not decorative; each addition closes a specific verification gap (Table 2).
Three changes deserve emphasis. First, the final-hash location moves into an external manifest: because
metadata injection changes the file that was signed, v1.2 contained an inherent tension between in-file
attestation keys and the hash of the file that contains them; v1.3 resolves it by letting the signed in-toto
manifest (which covers the whole bundle, external to the file) be the final digest's home [22], [21].
Second, sanitization becomes attested: the fields metadata_sanitized and cve_checked record that Gate 0
ran against the identified parser vulnerabilities, converting a private engineering step into a claim a third
party can require and audit [14], [15]. Third, the anchored block stops treating the log as a single trusted
party: consistency proofs and a witness quorum of at least two cosignatures are required, which is the
minimal configuration under which a malicious or compromised log cannot equivocate without
detection [17], [35].

4.3 Consistency rules
The schema is accompanied by consistency rules that make malformed attestations detectable before any
cryptography runs. The five v1.2 rules carry over: every entry in declared_capabilities must carry an
explicit status; slsa_level is valid only when slsa_level_defined is true; an ANCHORED_IN_REKOR
status requires non-empty log identifier, index, UUID, and tree size; the short_lived strategy requires
bounded certificate validity; and the default trust root is Sigstore/Fulcio [36]. We flag one tension inside
rule four that verification ought to enforce more strictly than the source does: the schema retains a
certificate_validity_hours bound of 72 from v1.2, while the public Fulcio instance issues certificates
with approximately ten-minute lifetimes [20]; we interpret 72 hours as an upper bound for private
deployments and recommend that verifiers require the public-good default unless the trust root explicitly
declares otherwise. To the carried-over rules, the v1.3 artifacts add three: metadata_sanitized must be
true (not merely present) for artifacts produced by the reference pipeline; cve_checked must name the
concrete CVE identifiers the sanitizer defends against; and an attestation claiming witness quorum must
carry at least that many distinct, valid cosignatures.
4.4 JSON as canonical source, GGUF as flat projection
GGUF metadata is a flat, typed key-value map: the format has no nested objects [1]. The framework
therefore designates the JSON document as the canonical schema source and projects it into the
container as a dotted, flat namespace — arkhe.attestation.verifiable.signed_at and so on — via the gguf
Python library's reader/writer interface [39] (Listing 3). The projection rule has a non-obvious
verification consequence that the package makes explicit: because the metadata lives inside the file, any
change to it changes the file's digest. Attestation keys therefore can never claim to contain the hash of
the file they inhabit; the digests they do carry refer to the pre-extension base (source block) and to
external bundles (manifest). This is the same self-reference paradox that Listing 5 encodes as a negative
test, and it is the engineering reason the schema's honesty is structural rather than declared.
5. The Four-Gate Verification Architecture
Verification in arkhe-verify, the Rust crate at the center of the complete project structure, is a four-gate
pipeline (Figure 3). The gates are ordered by dependence: sanitization before parsing, parsing before
hashing, hashing before signature checks, and everything before transparency-log checks. The crate is
deliberately small — it composes the ggus parser [32], the ct-merkle implementation of RFC 6962 proofs

5.1 Gate 0: metadata sanitization
Gate 0 exists because the first code to touch a model file is a parser, and Section 2 records what parsers
have done with hostile inputs [10], [11], [13], [14], [15]. The sanitizer enforces fixed limits before any
allocation: strings at most 1 MiB, arrays at most one million elements, at most ten thousand metadata
pairs, at most eight tensor dimensions, and a cumulative allocation ceiling of one gibibyte (Table 3).
Each limit maps to a known vulnerability class — uncontrolled allocation (the CVE-2026-65315
pattern), integer overflow (CVE-2025-53630), and count-field overflow (CVE-2024-23605) — and each
violation is a hard rejection, not a clamp. The gate ships twice: as a standalone Python script that can run
before signing in the pipeline, and as the Rust sanitize module that runs at verification time; both
implement the same limits so that the producer-side and consumer-side checks cannot drift apart
silently.

5.2 Gates 1 and 2: digest and signature
Gate 1 recomputes the artifact's SHA-256 and BLAKE3 digests and compares them against the values
recorded in the signed manifest; the source block preserves the pre- extension digest so that both stages
of the artifact's life are independently auditable [26], [27]. Gate 2 verifies the OpenSSF Model Signing
envelope: an in-toto Statement v1 whose subject list enumerates the bundle's files with their digests,
signed keylessly — a GitHub Actions OIDC token bound into a short-lived Fulcio certificate, recorded
in Rekor, and verifiable against the Sigstore trust root [21], [22], [16], [40]. Two properties of this envelope
matter for the model use case. The subject list covers every file in the bundle, so a signature cannot be
reused across a partially swapped set of artifacts; and the certificate's short lifetime bounds the window
in which a stolen signing session remains usable, complementing the schema's revocation block.
5.3 Gate 3: transparency log with witness quorum
Gate 3 is where v1.3 most materially departs from v1.2. The verifier now requires three properties, not
one: an inclusion proof that the artifact's entry is in the log's Merkle tree at a stated size; a consistency
proof that the tree at that size is a prefix of the current tree, establishing append-only behavior [17]; and a
witness quorum — at least two valid checkpoint cosignatures from independently configured witnesses,
matching the ecosystem's direction of travel in which Rekor v2 treats witness cosigning as a first-class
deployment component [35], [18]. The quorum is configured, not hard-coded, so an operator can raise it;
the tauri-side updater configuration of Section 8.2 mirrors the same field. Figure 4 depicts the full
structure, and Listing 2 shows the resulting obligations as implemented in the crate's verify_full routine.
The design assumption is explicit: the log operator is not automatically trusted, and a single-log
compromise must not suffice to produce an artifact that passes Gate 3.

5.4 Negative tests as executable specification
The crate's test suite encodes the fail-closed axiom as executable expectations (Table 4). Oversized
strings, oversized arrays, invalid magic numbers, missing consistency proofs, and insufficient witness
quorums must all be rejected; the tests assert that they are [36]. One test deserves singling out for its
epistemic neatness: final_artifact_does_not_contain_its_own_hash asserts that the artifact's bytes do not
contain the hex encoding of the artifact's own SHA-256 digest — a fixed-point impossibility that any
implementation claiming in-file final hashes would fail. The negative tests are the mechanism that keeps
the pipeline's failure semantics honest over time: they regress whenever a code change accidentally
introduces a default-allow path.

6.1 Thirteen steps

(step 9), witness-quorum verification (step 10), and Nostr identity verification (step 12). The delegation
brief specifies mandatory ordering for implementers, prioritizing the three critical items — Gate 0
sanitization, consistency plus witness verification, and npub pinning — before any convenience features

6.2 Hash-ordering invariants
The pipeline's central discipline is that digests have a direction. The base digest is computed before
extension; the final digest is computed after extension and never inside the artifact; the manifest
enumerates the bundle only after both exist; and the log entry anchors the signed manifest rather than an
ad-hoc structure. Inverting any two adjacent steps breaks verification in a detectable way: the served
bytes will not reproduce the anchored digest, which is exactly the failure the negative tests and the
checklist's acceptance criteria encode. The v1.3 move to an external manifest simplifies this discipline at
one point — the signed statement covers the whole bundle, so no in-file field needs to claim the final
digest — while preserving it everywhere else. The package's prohibitions state the corollaries
operationally: do not invent hashes; do not sign before sanitizing; do not publish before verification; and
do not trust the user interface — verify the payload independently [36], [28].
6.3 A tooling erratum, and what it demonstrates
During bibliographic verification for this article we identified an erratum in the checklist as written:
steps 9 and 10 cite rekor-cli verify --consistency and rekor-cli verify --witness-quorum 2, flags that do
not exist in the rekor v1 command- line interface. The actual interface performs inclusion, checkpoint,
and signed- entry-timestamp verification inside rekor-cli verify, and computes consistency evidence
through the separate rekor-cli logproof command [19]; witness-quorum verification is the province of the
witness ecosystem and Rekor v2 rather than a flag [35]. We flag this not as a defect of the methodology
but as its demonstration: the checklist specifies verification obligations, and the delegated executor must
map obligations to the tooling that actually exists — the same specify-don't-simulate rule applied to
tooling. The erratum also illustrates why every delegated step carries an acceptance criterion: an
executor that ran a nonexistent flag would fail step 9's exit-0 criterion immediately, rather than silently
skipping a verification.
6.4 The provenance chain
The pipeline emits docs/provenance.json, a four-record hash chain in which each record carries a
BLAKE3 record hash and the previous record's hash as prev_hash, with a genesis prev_hash of
sixty-four zeros [27], [36]. The records correspond to the pipeline's state transitions — header plus
attestation metadata, signature, Rekor anchoring, and Hashtree publication — making the chain
isomorphic to the WormGraph evidence structure of the surrounding Arkhe OS architecture [36]. The
chain's value is auditability across processes: an auditor can confirm that the artifact's publication claim
descends from the signing claim that descends from the metadata claim, with each link independently
recomputable.

7. Governance Enforcement: Safenet and FROST
Verification is epistemics; enforcement is politics of the execution path. The arkhe-governance crate
integrates Safenet, the Safe Ecosystem Foundation's on-chain security network, whose SafenetGuard
contract sits in front of every execTransaction call of a guarded Safe wallet and blocks transactions that
lack a valid attestation [31]. The integration's logic is a four-step fail-closed sequence: confirm the guard
is installed on the target Safe; request attestation for the transaction; validate the attestation's FROST
threshold signature over known oracle data; and only then submit. FROST — the Flexible
Round-Optimized Schnorr Threshold protocol, specified in RFC 9591 as an IRTF Crypto Forum
Research Group informational document [30] — provides the threshold property: the attestation is
produced by a quorum of independent signers and verifies as a single signature, so on-chain enforcement
does not require trusting any single operator.
The architectural claim, inherited from the Arkhe OS incident analyses, is that this moves security from
the warning path to the execution path [31], [28]: instead of showing an operator a warning that human
attention may or may not catch, the execution environment itself refuses to run the unsafe action. For
model artifacts the analogy is direct — a model whose attestation fails is not displayed with a warning
but is not loaded — and the revocation block's safenet_enforced strategy gives the schema a concrete
revocation mechanism: attestation validity is checked against network state at enforcement time, not
against a static certificate lifetime alone. The framework maps its quorum policies onto
ConstitutionStore thresholds, keeping the ratio strict (no quorum below two-thirds) and consistent with
the witness quorum of Section 5.3 [36].
8. Decentralized Distribution: Hashtree and Identity Pinning
8.1 Content-addressed publication
After verification, the artifact is published through Hashtree, the content-addressed storage layer that
distributes files over Nostr relays and serves them by content identifier [36]. Publication uses the htree
add and htree publish workflow; the CID binds the served bytes to the digests that Gate 1 verified, so the
decentralized distribution layer inherits rather than redefines integrity. The storage crate's client verifies
the Schnorr signature of the Nostr event that carries the mutable reference and checks that its author key
matches the configured trusted set, using NIP-19 bech32 npub encoding as the identity presentation
format [34].
8.2 npub pinning and verified updates
The distribution layer's critical control is npub pinning: the updater accepts release references only from
explicitly configured public keys. The tauri-side configuration in the package makes the parameters
explicit — relay endpoints, trustedNpubs, signature verification enabled, minimum two witnesses, and a
required consistency proof — so the desktop application's update path is governed by the same quorum

discipline as the model path [37]. This closes a loop that the framework considers essential: a verified
model distributed through an unverified channel would reinstate exactly the gap the pipeline eliminates,
and an update channel is the classic supply-chain pivot from a compromised dependency to
compromised hosts. The implementation priority list in the delegation brief marks npub pinning as
critical for precisely this reason: without it, updates from untrusted sources are accepted by default [36].
9. Local Inference: The Flare Engine
The pipeline's endpoint is execution, and execution is kept local. The frontend engine wraps the Flare
LLM runtime — a WASM-first browser inference engine with WebGPU acceleration [38] — in a loader
that attempts GPU initialization and falls back to WASM SIMD128 unconditionally, so the artifact runs
without any server component. The choice is attestation-relevant rather than merely ergonomic. First, it
keeps the verified artifact and the executing runtime in the same trust domain: no upload, no opaque
remote execution, no re-introduction of the trust-the-provider gap between verification and use. Second,
it makes the verifier's obligations symmetric with the runner's: the same metadata the verifier checked is
available to the runtime that loads the model. Third, it completes the sovereignty narrative that runs
through the surrounding Arkhe OS work — free firmware at the hardware layer, content-addressed
distribution at the network layer, on-chain governance at the coordination layer, and now attested local
inference at the model layer [36]. The fallback structure also models the framework's broader approach to
capability negotiation: degrade deterministically rather than fail open. Figure 6 summarizes the resulting
stack.

10. Counterarguments and Limitations

10.1 Attestation is not behavior
The strongest objection to the whole construction is that it verifies containers, not conduct. A model
whose weights encode harmful behavior passes every gate if the container is intact, properly signed, and
honestly anchored; the schema's empty capabilities list and PROMISE type exist precisely to prevent the
pipeline from being read as a behavioral guarantee. The disclaimer field states it in the artifact itself, and
the framework's roadmap (behavioral probes that would justify a VERIFIED type) remains future work
[36]. We regard this as the correct epistemic posture — an attestation that claimed behavior would be
unfalsifiable — but users must understand that Gate 1 through Gate 3 answer who produced and who
anchors an artifact, never what it will do.
10.2 Signed is not safe
Gate 0 defends against the parser vulnerabilities that are known and identified; it cannot defend against
zero-day memory-safety flaws in the underlying runtimes, and its numeric limits are engineering
judgments rather than derived optima. The 2024– 2026 record of Section 2 cuts both ways: it justifies
sanitization as necessary, and it implies that sanitization is not sufficient [10], [11], [12], [13], [14], [15]. The
pipeline's own honesty about this — signed is not safe is one of its stated mottos — is worth preserving
against the temptation to market the four gates as a security boundary in the strong sense.
10.3 Trust anchors remain
The pipeline relocates trust; it does not eliminate it. Verifiers trust the Sigstore root and the Fulcio PKI
[16], [20]; OIDC identities authenticate a workflow, not the good faith of its author; the witness quorum is
only as independent as its configuration, and an operator who configures two colluding witnesses has
recreated single-party trust with extra steps. The framework's answer — quorums as explicit, auditable
configuration via ConstitutionStore, with strict ratios [36] — is the right kind of answer, but the residual
is real and belongs in any deployment's threat model.
10.4 Certificate validity and the 72-hour question
The schema's carried-over certificate_validity_hours bound of 72 sits in tension with the public Fulcio
instance's approximately ten-minute certificates [20]. We read 72 hours as an upper bound appropriate to
private deployments and recommend that verifiers treat the public-good default as normative unless a
deployment's trust root declares otherwise. The discrepancy is documented here because the package's
own consistency rules demand that declared bounds be enforced; a rule that permits what the ecosystem
never issues is a rule that should be tightened, and we say so in Section 11.
10.5 Delegation residuals
The methodology's honesty has a boundary: a delegation package cannot verify its own delegated
execution. The acceptance criteria map obligations to observable exit codes and artifacts, but the AI
coder (or human executor) who runs the thirteen steps is outside the package's epistemic control; the
checklist's prohibitions are norms, not mechanics. Two mitigations exist in the structure — the negative
tests re-run at verification time on the consumer side, and every claim the executor makes is
re-checkable by a third party from the published evidence — but the residual trust in the executor is real
and should be recorded as such.
10.6 Engineering and ecosystem risks
Three practical risks round out the picture. The small-community dependencies (ggus, ct-merkle)
concentrate review burden [32], [33]. Quorum and relay liveness are operational dependencies: a


=== PAGINA 18 ===
Specify, don't simulate — the arkhe.gguf v1.3 verification pipeline
Page 18
distribution layer that requires two witness cosignatures and healthy Nostr relays has an availability
profile that single- operator infrastructure does not. And the GGUF projection of a five-block schema
adds metadata weight to every artifact; the dotted namespace is compact, but the inclusion proofs and
manifest references it points to must remain retrievable for the attestation to be checkable years later,
which is an archival commitment as much as a cryptographic one.
10.7 What the threat model excludes
Finally, the boundary of the model: training-data poisoning, weight-level backdoors that trigger on
distributed inputs, and all behavioral attacks leave no trace in container metadata. The pipeline is
supply-chain infrastructure; it is not, and does not claim to be, an alignment or auditing technique. The
scanner-evasion record of Section 2.2 — where even dedicated behavioral scanners were bypassed [8],
[9] — suggests that behavioral verification is a hard open problem, which reinforces rather than
undermines the decision to build the verifiable floor first.
11. Conclusions and Future Work
The arkhe.gguf framework demonstrates that a verifiable floor for open-weight model distribution is
achievable with existing, institutionally maintained primitives — Sigstore, RFC 6962 transparency,
in-toto envelopes, SLSA vocabulary — provided two things are added: a binding to the specific
container format and parser threat model of GGUF, and an honesty discipline that keeps specification,
execution, and declaration separately auditable. The four-gate pipeline implements the first; the
delegation methodology and the empty capabilities list implement the second. Schema v1.3's additions
— the source block, the external manifest hash location, sanitization attestation, consistency proofs, and
witness quorum — each close a gap that v1.2 left open, and the negative tests make the pipeline's failure
semantics executable rather than aspirational.
Future work follows from the limitations, and the framework states most of it itself. First, fill the
remaining placeholders by execution: a base model, a real trust root, real log entries, and the resulting
production artifact, each adding a column of verified evidence to the ledger. Second, tighten the
consistency rules that this review found loose — the certificate-validity bound of Section 10.4 and the
rekor-cli command mapping of Section 6.3 are the two concrete errata. Third, move from PROMISE
toward VERIFIED: behavioral probes whose results would be recorded in the attested block, with the
same honesty rule that a probe not run leaves the field empty. Fourth, publish the public catalog of
verified GGUF artifacts — the blob-database pattern the surrounding LibrePhone work models — so
that verification becomes a property of a shared infrastructure rather than a per-consumer chore [36].
Fifth, propose the arkhe.attestation.* metadata convention upstream to the llama.cpp and Hugging Face
communities, where a shared namespace would let independent verifiers interoperate. Sixth, formalize
the gate implementations — the Rust crates are small enough that machine-checked proofs of the
fail-closed property are plausible. The broader claim the framework stakes out survives every caveat we
have raised: in a distribution ecosystem that today operates on promises, the verifiable floor is not the
ceiling — but without it, there is nothing to build on.
