# Arkhe Full Stack — Arquitectura e Engenharia

O Arkhe foi desenhado como um kernel de verificação. A expansão que propões não é abandonar esse princípio — é **aplicá-lo a toda a pilha de IA**. Cada módulo que "o Arkhe não faz" passa a ser um módulo que o Arkhe faz **com verificação embutida**. RAG que é auditável. Serving que é atestado. Treino que é rastreável. Chat que é verificável.

O princípio mantém-se: **nenhuma acção é executada sem verificação, e nenhuma verificação é contornada**. O que muda é o âmbito.

---

## 1. Visão

```
Arkhe = Kernel de confiança + Pilha completa de IA com verificação nativa

Cada artefacto produzido em qualquer camada tem:
  • hash (BLAKE3)
  • proveniência (WormGraph)
  • assinatura (Ed25519)
  • âncora externa (Rekor/Sigstore)
  • verificação portátil (WASM)
```

A diferença entre o Arkhe expandido e uma pilha de IA convencional é que, no Arkhe, **cada passo é verificável independentemente**. O utilizador pode provar que o modelo foi treinado com o dataset declarado, que o RAG recuperou os chunks correctos, que o agente autorizou a tool certa.

---

## 2. Arquitectura em seis planos

```
┌─────────────────────────────────────────────────────────────────┐
│  P5 — SECURITY PLANE                                            │
│  Threat model · PII · Prompt injection · Compute attestation    │
└────────────────────────────┬────────────────────────────────────┘
                             │ (cross-cutting)
┌────────────────────────────▼────────────────────────────────────┐
│  P4 — OPERATIONS PLANE                                          │
│  Experiment tracking · Drift · Eval · Cost · Cache              │
└────────────────────────────┬────────────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────────────┐
│  P3 — APPLICATION PLANE                                         │
│  Chat · RAG · Agent runtime · MCP gateway                       │
└────────────────────────────┬────────────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────────────┐
│  P2 — MODEL PLANE                                               │
│  Training · Fine-tuning · Serving · Registry · Router           │
└────────────────────────────┬────────────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────────────┐
│  P1 — DATA PLANE                                                │
│  Ingestion · Lineage · Versioning · Quality · Vector store      │
└────────────────────────────┬────────────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────────────┐
│  P0 — TRUST KERNEL                                              │
│  WormGraph · Attestation · Governance · Verification            │
└─────────────────────────────────────────────────────────────────┘
```

**Regra fundamental:** cada plano depende apenas dos planos abaixo. Nenhum plano contorna o kernel. Nenhuma operação é executada sem produzir um artefacto verificável.

---

## 3. Módulos por plano

### P0 — Trust Kernel

| Crate | Função | Estado |
|:---|:---|:---|
| `arkhe-core` | Tipos, erros, traits, invariantes | ✅ |
| `arkhe-wormgraph` | Grafo causal append-only, MMR | ✅ |
| `arkhe-verify` | Motor de verificação fail-closed | ✅ |
| `arkhe-verify-wasm` | Verificação portátil em WebAssembly | ✅ |
| `arkhe-model-attestation` | Atestação GGUF, canonicalização | ✅ |
| `arkhe-governance` | ConstitutionStore, quórum, autoridade | ✅ |
| `arkhe-identity` | DIDs, wallets, Ed25519 | ✅ |

**Contrato P0:** qualquer artefacto produzido nos planos superiores é registado no WormGraph com `record_hash`, `prev_hash` e assinatura. A verificação é sempre possível sem acesso ao Arkhe.

### P1 — Data Plane

| Crate | Função | O que verifica |
|:---|:---|:---|
| `arkhe-ingest` | Ingestão de dados de APIs, ficheiros, streams | Proveniência de origem |
| `arkhe-lineage` | Lineage de transformações | Cada transformação é um record |
| `arkhe-versioning` | Versionamento de datasets | Cada versão tem hash |
| `arkhe-quality` | Gates de qualidade (schema, completude, drift) | Falha fail-closed |
| `arkhe-vector-store` | Armazenamento de embeddings | Proveniência do modelo de embedding |
| `arkhe-embedding-provenance` | Rastreio de modelo, dimensão, índice | Registo no WormGraph |

**Contrato P1:** cada dataset tem um `dataset_hash` ancorado no WormGraph. Cada transformação produz um novo `record_hash`. A linhagem é reconstruível.

### P2 — Model Plane

| Crate | Função | O que verifica |
|:---|:---|:---|
| `arkhe-trainer` | Orquestração de treino | Hardware, dataset, hiperparâmetros |
| `arkhe-finetune` | LoRA, fine-tuning | Base model, adapter hash |
| `arkhe-serving` | Inference APIs (vLLM, TGI, Ollama) | Modelo atestado em runtime |
| `arkhe-registry` | Registo de modelos | Cada versão tem hash + assinatura |
| `arkhe-router` | Routing entre modelos | Decisão registada + justificada |
| `arkhe-compute-attestation` | Atestação de hardware (TEE, GPU) | Prova de execução em hardware declarado |

**Contrato P2:** nenhum modelo é servido sem estar no registry. Nenhum modelo é servido sem atestação válida. Nenhum routing é executado sem registo da decisão.

### P3 — Application Plane

| Crate | Função | O que verifica |
|:---|:---|:---|
| `arkhe-chat` | Interface de chat (SSE, streaming) | Cada resposta tem envelope |
| `arkhe-rag` | RAG completo (chunking, retrieval, reranking) | Cada chunk tem proveniência |
| `arkhe-agent` | Runtime de agentes com tools | Cada tool call é autorizada |
| `arkhe-mcp` | Gateway MCP | Tools expostas são verificáveis |
| `arkhe-memory` | Memória episódica de agente | Cada memória tem hash |

**Contrato P3:** cada resposta de chat tem um `envelope_hash`. Cada chunk recuperado tem um `record_hash` verificável contra o original. Cada tool call tem um `authorization_proof`. Cada memória é append-only.

### P4 — Operations Plane

| Crate | Função | O que verifica |
|:---|:---|:---|
| `arkhe-experiment-tracker` | Tracking de runs de treino | Hiperparâmetros, métricas, dataset hash |
| `arkhe-drift-detect` | Detecção de drift | Input drift, output drift, concept drift |
| `arkhe-eval` | Eval suite (golden set, LLM-as-judge) | Reprodutibilidade de scores |
| `arkhe-judge-verify` | Verificação de LLM-as-judge | Modelo juiz pinado, prompt pinado |
| `arkhe-cost-tracker` | Custo por chamada, routing | Registo append-only |
| `arkhe-cache` | Cache semântico | Hit/miss, false hits, verificação |

**Contrato P4:** cada eval produz um `eval_hash`. Cada decisão de routing é registada. Cada hit de cache é verificável.

### P5 — Security Plane

| Crate | Função | O que verifica |
|:---|:---|:---|
| `arkhe-threat-model` | MITRE ATLAS, OWASP RRM | Cada ataque detectado é classificado |
| `arkhe-pii` | Detecção e redacção de PII | Redacção antes do modelo |
| `arkhe-prompt-injection` | Detecção de injection | Fail-closed |
| `arkhe-boundary` | Invariantes I_REG1–4 | Verificação contínua |

**Contrato P5:** nenhuma chamada de modelo é feita sem PII redigida. Nenhuma tool é invocada sem verificação de injection. Nenhuma operação financeira é executada pelo Arkhe.

---

## 4. Contratos entre planos

Cada plano comunica com o plano abaixo através de **interfaces bem definidas**, não de chamadas directas.

```
P5 (Security) ─── intercepta ───► P4, P3, P2, P1
P4 (Operations) ─── observa ────► P3, P2, P1
P3 (Application) ─── invoca ────► P2, P1
P2 (Model) ──────── consome ────► P1
P1 (Data) ──────── ancora ──────► P0
P0 (Kernel) ─────── verifica ───► todos
```

### Exemplo: fluxo de uma query RAG

```
1. Utilizador → P3 (arkhe-chat)
2. P3 → P5 (arkhe-pii): redacção de PII
3. P3 → P4 (arkhe-cache): hit ou miss
4. P3 → P1 (arkhe-vector-store): retrieval
5. P1 → P0 (arkhe-wormgraph): verificar record_hash dos chunks
6. P3 → P2 (arkhe-router): escolher modelo
7. P2 → P0 (arkhe-model-attestation): verificar atestação do modelo
8. P2 → P4 (arkhe-cost-tracker): registar custo
9. P3 → P0 (arkhe-wormgraph): ancorar resposta
10. P3 → utilizador: resposta com envelope_hash
```

Cada passo produz um artefacto. Cada artefacto é verificável. Nenhum passo contorna o kernel.

---

## 5. Invariantes transversais

Estes invariantes aplicam-se a **todos os planos**:

```
INV-ARKHE-01: Todo o artefacto tem hash BLAKE3
INV-ARKHE-02: Todo o artefacto tem proveniência (prev_hash)
INV-ARKHE-03: Todo o artefacto é assinado (Ed25519)
INV-ARKHE-04: Todo o artefacto é ancorado externamente (Rekor)
INV-ARKHE-05: Toda a verificação é fail-closed
INV-ARKHE-06: Nenhuma operação financeira é executada pelo Arkhe
INV-ARKHE-07: Nenhum modelo é servido sem atestação
INV-ARKHE-08: Nenhuma tool é invocada sem autorização
INV-ARKHE-09: Nenhuma resposta é devolvida sem envelope
INV-ARKHE-10: Nenhum dado é processado sem lineage
```

**Violação de qualquer invariante = rejeição da operação.** Não há modo degradado.

### Testes

| Tipo | Onde | Ferramenta |
|:---|:---|:---|
| Unit | Cada crate | `cargo test` |
| Property | `arkhe-core`, `arkhe-wormgraph` | `proptest` |
| Invariantes | Cada crate | Falsificadores |
| Integração | `tests/` | `cargo test --test` |
| E2E | `tests/e2e/` | `pglite-oxide` + MCP Inspector |
| Cripto | `arkhe-verify` | Golden vectors |

### CI Pipeline

```yaml
stages:
  - check:    cargo check --locked --workspace
  - fmt:      cargo fmt --check
  - clippy:   cargo clippy -- -D warnings
  - test:     cargo test --locked --workspace
  - deny:     cargo deny check
  - audit:    cargo audit --locked
  - invariants: scripts/verify_invariants.sh
  - e2e:      scripts/run_e2e.sh
```

Nenhum merge passa sem todos os gates verdes.

A arquitetura tem uma ideia forte — **kernel verificável + componentes substituíveis** — mas eu **não congelaria esta versão ainda**. A auditoria contra o próprio documento e contra o repositório acessível mostra algumas contradições estruturais que precisam ser resolvidas antes de virar arquitetura normativa.

O primeiro ponto é de estado real. O documento declara F0–F1 implementados e lista crates como `arkhe-wormgraph`, `arkhe-verify-wasm`, `arkhe-model-attestation`, `arkhe-governance` e `arkhe-identity` como existentes. Texto colado Texto colado Mas o fluxo RAG faz `P3 → P5` para PII, enquanto o diagrama afirma que P5 “intercepta” P3/P2/P1. Texto colado Texto colado Isso quebra a direção declarada. O P0 também precisa de inversão de dependência. O documento diz que P0 “verifica todos”, mas ao mesmo tempo que P0 não depende de nada. Texto colado Texto colado Isso só funciona se P0 verificar **artefatos genéricos e contratos estáveis**, não conhecer tipos concretos de RAG, training, chat ou serving. Os invariantes transversais também estão fortes demais em alguns pontos. O documento exige BLAKE3, `prev_hash`, assinatura Ed25519 e âncora Rekor para **todo artefato**. Texto colado Isso conflita com a realidade do próprio Arkhe: C2PA, SHA-256, certificados X.509, Solana e outros protocolos possuem algoritmos e trust models próprios. Eu substituiria esses invariantes por uma política algorítmica versionada: todo artefato possui um digest explicitamente identificado por algoritmo; todo artefato persistente tem provenance linkage; todo artefato que cruza um trust boundary tem autenticação verificável; e checkpoints/raízes podem ser ancorados externamente. Não é necessário assinar e publicar no Rekor cada chunk, cache hit ou token de streaming individualmente.

O mesmo vale para `INV-ARKHE-04`. “Todo artefato é ancorado externamente” criaria custo, latência e dependência operacional externa enormes. Para WormGraph/MMR, é mais coerente:

\[
Artifact \rightarrow AppendOnlyGraph
\]

e periodicamente:

\[
MMRRoot_t \rightarrow ExternalAnchor
\]

Assim você preserva verificabilidade sem transformar Rekor numa dependência síncrona de cada operação.

`INV-ARKHE-05`, “toda verificação é fail-closed”, está correto **nas decisões que afetam confiança**. Mas “qualquer falha em qualquer componente = rejeição da operação” é excessivo. Se o cost tracker estiver temporariamente indisponível, isso não deveria necessariamente impedir uma inferência que já passou por autenticação, provenance e policy, salvo se metering for parte do contrato comercial daquela operação. Eu reformularia para:

\[
TrustCriticalVerificationFailed
\Rightarrow Reject
\]

e manteria falhas não críticas explicitamente observáveis, nunca silenciosas.

`INV-ARKHE-06`, por outro lado, está muito bem alinhado com a fronteira regulatória que já definimos: “nenhuma operação financeira é executada pelo Arkhe”. Texto colado Eu fortaleceria isso com a formulação de capacidade:

\[
ArkheControlledCapability \cap ClientFundMovement = \varnothing
\]

porque “não executar operação financeira” precisa cobrir também PDA authority, signer services e submissão indireta, não apenas possuir uma private key.

Há mais quatro ajustes que considero necessários antes do freeze:

- `INV-ARKHE-07`: separar **model artifact attestation** de **compute/hardware attestation**. Provar qual GGUF/model hash está carregado é uma coisa; provar que uma inferência efetivamente ocorreu naquela GPU/TEE é muito mais difícil.
- `INV-ARKHE-08`: tool authorization deve incluir principal, scope, request digest, policy version e expiration; “autorizada” sozinho é insuficiente.
- `INV-ARKHE-09`: uma resposta streaming precisa de protocolo próprio, porque você não conhece o envelope final antes do fim do stream.
- `INV-ARKHE-10`: “nenhum dado é processado sem lineage” deve começar no **ingress boundary**; bytes precisam ser recebidos antes de poderem ser hashados e registrados.

A decisão estratégica de virar “full AI stack” também merece cautela. O texto assume que o Arkhe deve fazer RAG, serving, training, chat, vector store, routing, eval, drift, PII, injection detection e compute attestation. Texto colado Isso expande drasticamente a superfície de auditoria e transforma Arkhe de uma infraestrutura diferenciada de provenance em concorrente de dezenas de produtos maduros. A frase mais forte do documento é, na verdade, outra: **“the kernel is the invariant; everything else is replaceable.”** Texto colado Eu levaria isso literalmente: Arkhe pode oferecer implementações próprias de RAG/serving/training, mas o protocolo deveria permitir que LangChain, vLLM, TGI, Ollama, pgvector, Pinecone etc. se conectem sem perder verificação.

Então o posicionamento mais defensável seria:

> **Arkhe is a verifiable AI execution fabric: a trust kernel plus replaceable, provenance-aware adapters and reference implementations across data, models, applications and operations.**

Isso mantém a ambição full-stack sem obrigar o projeto a substituir cada componente da indústria.

## 2. Aprimoramentos da Pesquisa

### 2.1 WormGraph e MMR: Validação Científica

O WormGraph é descrito como um "grafo causal append-only com MMR" no Arkhe. A pesquisa confirmou que MMR (Merkle Mountain Range) é uma estrutura criptográfica optimizada para dados append-only, com provas de inclusão de O(log n) e suporte a múltiplas funções de hash (SHA-256, BLAKE3, Argon2).

O artigo académico "ARKHE: A Verifiable Trust Architecture for Autonomous AI Agents" (Zenodo, Setembro 2026) confirma que o WormGraph é um "append-only causal evidence graph anchored to external transparency logs" e que o Arkhe é "architecturally coherent but pre-product".

**Recomendação:** Usar BLAKE3 como hash primário (já implementado no WormGraph), mas permitir SHA-256 como fallback para interoperabilidade com C2PA.

### 2.2 ML-DSA-65: Tamanhos e Performance

A pesquisa confirmou os dados do documento IPv7:

| Parâmetro | ML-DSA-44 | ML-DSA-65 | ML-DSA-87 |
|:---|:---|:---|:---|
| Chave pública | 1.312 bytes | **1.952 bytes** | 2.592 bytes |
| Assinatura | 2.420 bytes | **3.309 bytes** | 4.627 bytes |
| Segurança NIST | Categoria 2 | **Categoria 3** | Categoria 5 |

O ML-DSA-65 é ~46× maior que ECDSA em assinatura e ~59× maior em chave pública. A performance de verificação é de ~1.000 verificações/segundo, com assinatura ~25-30% mais lenta que Ed25519.

**Recomendação:** Usar ML-DSA-65 apenas para artefactos de longo prazo (modelos, datasets). Para envelopes de sessão e tokens efémeros, usar Ed25519 (rápido e compacto). A combinação híbrida (Ed25519 + ML-DSA-65) oferece segurança pós-quântica sem sacrificar performance em operações de alta frequência.

### 2.3 C2PA: Integração com Provenance de Conteúdo

O C2PA (Coalition for Content Provenance and Authenticity) é o padrão ISO 22144:2026 para Content Credentials. A arquitectura usa "assertions" como unidades de informação, manifestos que vinculam assertions, claims e assinaturas, e um trust model baseado em X.509.

**Recomendação:** O Arkhe deve tratar C2PA como **formato de exportação/importação** para proveniência de conteúdo, não como concorrente. O `arkhe-c2pa-bridge` já existente no repositório é o ponto de integração.

### 2.4 SLSA: Provenance de Software e Modelos

SLSA (Supply-chain Levels for Software Artifacts) define níveis L1–L3 para integridade de supply chain. A extensão para AI agents propõe vincular três supply chains independentes:

1. **Build de software** (SLSA, in-toto)
2. **Identidade do modelo** (hash criptográfico dos pesos)
3. **Ambiente de runtime** (RATS evidence, RFC 9334)

O documento da IETF "Agent Trust Negotiation" (Maio 2026) formaliza isso num `Provenance Attestation` com `build`, `model` e `runtime`.

**Recomendação:** O Arkhe deve adoptar SLSA v1.0 como formato de provenance para o P2 (Model Plane) e integrar RATS para atestação de runtime.

### 2.5 Rekor: Anchoring em Transparency Logs

O Sigstore Rekor é um transparency log purpose-built para supply chain de software, com provas de inclusão e consistência contra uma Merkle tree. O modelo de anchoring periódico de Merkle roots é o padrão recomendado.

**Recomendação:** Implementar anchoring em dois níveis:

- **Rekor** para artefactos de software (modelos, código, configurações)
- **RFC 3161 TSA** para timestamps legais (eIDAS, EU AI Act)

### 2.6 TEE e Atestação de Hardware

A pesquisa revelou avanços significativos em atestação de GPU TEE:

- **NVIDIA H100 Confidential Computing** com sub-second finality
- **Attested Inference Receipt (AIR)** como perfil COSE/CWT para inferência confidencial
- **NVIDIA Remote Attestation Service (NRAS)** que verifica GPU hardware reports e CPU TEE measurements contra reference integrity manifests
- **Attested Confidential Inference (ACI)** que vincula GPU TEE remote-attestation a signed model-provenance records

**Recomendação:** O `arkhe-compute-attestation` deve suportar:

- Intel TDX e AMD SEV-SNP para CPU TEE
- NVIDIA H100/H200 Confidential Computing para GPU TEE
- Formato AIR (Attested Inference Receipt) para recibos de inferência

### 2.7 RAG Verificável

A pesquisa identificou frameworks emergentes para RAG auditável:

- **raglineage**: trata RAG como problema de data lineage, com answer auditing e reconstrução de proveniência
- **Hyphae v2**: hash-chained verbatim quotation com Ed25519 head anchor
- **TRACE**: reconstrução forense criptograficamente verificada de proveniência de decisão em sistemas multi-agente

**Recomendação:** Integrar estes padrões no `arkhe-rag`, garantindo que cada chunk recuperado tem `record_hash` verificável contra o original.

### 2.8 Autorização de Tools

A pesquisa identificou protocolos emergentes:

- **Stipul**: intercepta tool calls, enforça policy e produz cadeia de prova criptográfica
- **Proof-Carrying Agent Actions (PCAA)**: acções irreversíveis requerem prova para cada obrigação de licenciamento
- **Verifiable Agent Protocol (VAP)**: intent-bound admission control para tool invocation

**Recomendação:** O `arkhe-agent` deve adoptar o modelo PCAA: cada tool call produz um `AuthorizationProof` com principal, scope, request digest, policy version e expiration.

### 2.9 Fail-Closed para Prompt Injection

A pesquisa confirmou que o padrão da indústria é **fail-closed** para guardrails de prompt injection. O ToolFence formaliza isso como "capability-authorization problem with a safe default".

**Recomendação:** O `arkhe-prompt-injection` deve ser fail-closed por omissão, com opt-out explícito apenas para ambientes controlados.

### 2.10 PII Redaction

A pesquisa mostrou que PII redaction antes da inferência é prática padrão, com redacção reversível (placeholders que são restaurados após a resposta).

**Recomendação:** O `arkhe-pii` deve implementar redacção reversível com placeholders estáveis, permitindo que o modelo processe texto sanitizado e o output seja restaurado.

### 2.11 Vector Store com Proveniência

A pesquisa identificou **VectorPin**, um protocolo criptográfico de proveniência para embeddings: cada embedding é vinculado ao seu conteúdo fonte e modelo produtor via assinatura Ed25519, e qualquer modificação pós-embedding quebra a verificação.

**Recomendação:** O `arkhe-vector-store` deve adoptar o modelo VectorPin: cada embedding tem assinatura sobre representação canónica de bytes, vinculando source content + model ID + dimension.

## 1. Correções Materiais Aplicadas

### 1.1 C2PA e ISO 22144

A afirmação anterior de que C2PA é "ISO 22144:2026" estava incorreta. A ISO classifica **ISO/CD 22144** como *under development*, estágio **30.99** (CD aprovado para registo como DIS), com data de 2024-10-28. Não é uma International Standard publicada.

A especificação técnica atual do C2PA é a **2.4, de abril de 2026**.

**Redação corrigida:**

> "C2PA Content Credentials 2.4 is the current technical specification. Its architecture is being standardized through ISO 22144, which remains under development and is not yet a published International Standard."

### 1.2 Mapa de Status: Regra de Evidência

A inconsistência entre a secção 1.1 (que classificava corretamente módulos não comprovados como `TARGET`) e a secção 3.4 (que declarava crates como `✅ Implementado`) foi resolvida com uma regra simples:

\[
Implemented \iff RepositoryEvidence \land BuildEvidence \land TestEvidence
\]

"Existe conceitualmente" ou "há código equivalente" não basta. A tabela de status abaixo reflecte esta regra.

### 1.3 Maturidade dos Padrões Emergentes

| Padrão | Classificação Corrigida |
|:---|:---|
| **ATN** (Agent Trust Negotiation) | Internet-Draft experimental, publicado em Maio de 2026, expira em 30 de Novembro de 2026 |
| **AIR** (Attested Inference Receipt) | Internet-Draft RATS, versão 01 de Março de 2026; não substitui verificação de evidência de plataforma |
| **PCAA** (Proof-Carrying Agent Actions) | Publicação peer-reviewed em *Scientific Reports* (2026), mas ainda um modelo de governança, não um protocolo de indústria consolidado |
| **VectorPin** | Open protocol com implementações de referência em Python, Rust e TypeScript; não é um padrão estabelecido |

### 1.4 ML-DSA-65: Performance

Os tamanhos estão coerentes com FIPS 204. A performance **não deve ser apresentada como propriedade geral do algoritmo**. Benchmarks variam enormemente por implementação e hardware:

- **GPU (NVIDIA A4000)**: ~3,2 milhões de verificações/segundo
- **CPU (referência C)**: ~371.420 verificações/segundo
- **Handshakes TLS**: ~644,5 ML-DSA-65 handshakes/segundo

**Redação corrigida:** Registar apenas tamanhos e security category como normativos. Performance é benchmark Arkhe-specific, não propriedade do algoritmo.

## 2. Aprimoramentos Adicionais

### 2.1 Digest Versionado (em vez de "Fallback")

A expressão "BLAKE3 primário, SHA-256 fallback" foi substituída por:

\[
Digest = (AlgorithmId, DigestBytes)
\]

Cada profile define algoritmos permitidos. C2PA pode exigir SHA-256 em determinado contexto; WormGraph usa BLAKE3. Não há "fallback" implícito que permita troca silenciosa de algoritmo.

### 2.2 Rekor vs RFC 3161

A afirmação "RFC 3161 = timestamps legais/eIDAS" era forte demais. A distinção correta:

- **Rekor**: transparency log para supply chain. O Rekor v2 **não carrega timestamp inline** (o "SET" do v1 foi removido); um bundle precisa de tempo confiável de uma **RFC 3161 TSA separada**.
- **RFC 3161**: só ganha peso jurídico específico quando associado a uma TSA e ao regime aplicável.

**Recomendação:** Implementar anchoring em dois níveis: Rekor para artefactos de software; RFC 3161 TSA para timestamps legais, quando aplicável.

### 2.3 ComputeAttestation no Model/Runtime Plane

`ComputeAttestation` permanece semanticamente no **Model/Runtime Plane**, mesmo que Security consuma sua evidência. Isso evita que P5 se torne dependente de toda a pilha.

### 2.4 Diagrama de Bus para P4/P5

O diagrama anterior, embora chamasse P4/P5 de "cross-cutting", ainda os mostrava numa cadeia vertical. A correção é representá-los como **buses/interfaces laterais**, não como planos hierárquicos:

```
                    ┌─────────────────────────────┐
                    │  P5 — SECURITY BUS          │
                    │  (intercepta via interfaces) │
                    └────────────┬────────────────┘
                                 │
┌────────────────────────────────┼────────────────────────────────┐
│  P3 — APPLICATION PLANE        │                                │
│  Chat · RAG · Agent · MCP      │                                │
└────────────────────────────────┼────────────────────────────────┘
                                 │
┌────────────────────────────────┼────────────────────────────────┐
│  P2 — MODEL PLANE              │                                │
│  Training · Serving · Registry │                                │
└────────────────────────────────┼────────────────────────────────┘
                                 │
┌────────────────────────────────┼────────────────────────────────┐
│  P1 — DATA PLANE               │                                │
│  Ingestion · Lineage · Vector  │                                │
└────────────────────────────────┼────────────────────────────────┘
                                 │
┌────────────────────────────────▼────────────────────────────────┐
│  P0 — TRUST KERNEL (contratos genéricos)                        │
│  ArtifactEnvelope · EvidenceRecord · PolicyDecision             │
└─────────────────────────────────────────────────────────────────┘

                    ┌─────────────────────────────┐
                    │  P4 — OPERATIONS BUS        │
                    │  (observa via eventos)      │
                    └─────────────────────────────┘
```

O bus é ortogonal aos planos verticais, permitindo que P4 e P5 observem e interajam sem criar dependências hierárquicas.

\[

\[

\]

InclusionProof

\]

Isso evita colocar estado global da árvore dentro de cada registro.

### 4. `AuthorizationProof` não deveria ser confundido com `PolicyDecision`

`PolicyDecision` é uma boa primitive genérica:

\[

\]

Mas uma tool call necessita de algo mais específico.

\]

como resultado genérico do policy engine e faria:

\[
AuthorizationProof =
Bind(

Tool,
Scope,
RequestDigest,
PolicyVersion,
DecisionId,
IssuedAt,
ExpiresAt
)
\]

Uma decisão `Allow` pode existir sem nunca ser consumida; o `AuthorizationProof` demonstra que uma ação concreta foi autorizada sob aquela decisão.

\]

\]

## 2. `ArtifactEnvelope`: Autenticação Condicional

### 2.1 Problema

O struct proposto exige `SignatureProof` para **todo** artefato. Isso contradiz `INV-ARKHE-03` (`CrossesTrustBoundary ⇒ VerifiableAuthentication`), que condiciona a autenticação ao cruzamento de uma fronteira de confiança.

### 2.2 Correção

A abstração conceitual deve ser:

\[
AuthenticationProof = Signature \;|\; Attestation \;|\; AuthenticatedChannelBinding \;|\; \dots
\]

O kernel não assume que toda autenticação será Ed25519, X.509 ou ML-DSA. O `ArtifactEnvelope` passa a ter:

```rust
pub struct ArtifactEnvelope {
    pub artifact_id: ArtifactId,
    pub digest: Digest,              // (AlgorithmId, DigestBytes)
    pub provenance: ProvenanceLink,
    pub authentication: Option<AuthenticationProof>, // exigido pela policy
    pub anchor: Option<ExternalAnchor>,
    pub policy_ref: PolicyRef,
}
```

A autenticação é exigida **pela policy quando ocorre um trust boundary**, não pelo tipo universal.

## 3. `EvidenceRecord`: Digest Ágil e Decomposição MMR

### 3.1 Digest Ágil

A v2.1 estabelece `Digest = (AlgorithmId, DigestBytes)` mas depois fixa `envelope_hash: Blake3Hash`. Isso cria uma exceção desnecessária dentro do kernel.

**Correção:**

```rust
pub struct EvidenceRecord {
    pub record_id: RecordId,
    pub envelope_digest: Digest,     // não Blake3Hash
    pub prev_hash: Option<Digest>,
    pub timestamp: UnixTimestamp,
    pub witness: WitnessProof,
}
```

O profile WormGraph determina `AlgorithmId = BLAKE3`, mas BLAKE3 não faz parte do tipo universal. A distinção é:

\[
KernelContract \neq WormGraphProfile
\]

### 3.2 Decomposição MMR

O `EvidenceRecord` representa um **registro causal** (digest, prev_hash, timestamp, witness). Não representa uma prova MMR completa. A arquitetura limpa separa:

\[
EvidenceRecord \rightarrow MMRLeaf \rightarrow InclusionProof \rightarrow Checkpoint \rightarrow ExternalAnchor
\]

Isso evita colocar estado global da árvore dentro de cada registro e permite:

\[
VerifyInclusion(record, proof, checkpoint) = true
\]

\[
VerifyAnchor(checkpoint, externalEvidence) = true
\]

A especificação IETF `draft-bryce-cose-merkle-mountain-range-proofs-01` (expirada em Maio de 2025, mas ainda referência técnica) define a codificação COSE para provas MMR, com validação estrita de fronteiras de montanha, comprimento de caminho, direção de irmãos e root final. O Arkhe pode adotar este formato como base para `InclusionProof` e `Checkpoint`.

## 4. `AuthorizationProof`: Separação de `PolicyDecision`

### 4.1 Problema

`PolicyDecision` é uma primitive genérica (`Allow | Deny | Abstain`), mas uma tool call necessita de algo mais específico. O artigo *Proof-Carrying Agent Actions* (PCAA), publicado em *Scientific Reports* (2026), formaliza exatamente esta distinção: cada ação governada carrega um **Action Certificate** tipado que um checker independente do planner deve aceitar antes da execução.

### 4.2 Correção

Manter `PolicyDecision` como resultado genérico do policy engine e definir:

\[
AuthorizationProof = Bind(Principal, Tool, Scope, RequestDigest, PolicyVersion, DecisionId, IssuedAt, ExpiresAt)
\]

O invariante resultante:

\[
ExecutedToolCall \Rightarrow ValidAuthorizationProof \land Proof.requestDigest = ExecutedRequestDigest
\]

\[
ProofExpired \lor DigestMismatch \lor ScopeMismatch \Rightarrow Reject
\]

O PCAA usa um *trusted execution shim* que deriva o conjunto de obrigações do contrato de tool e vincula o certificado à invocação exata com um commitment canónico SHA-256. O Arkhe pode adotar o mesmo modelo: o `AuthorizationProof` é o artefato verificável que liga a decisão de policy à ação concreta.

## 5. `INV-ARKHE-08`: Compute Attestation Condicional

### 5.1 Problema

A formulação "Nenhum modelo é servido sem compute attestation válida" é universalmente forte. O IETF `model_attestation Block for Agent Action Capsules` (Outubro 2026) define um bloco opcional que carrega runtime extensions, incluindo o model-serving runtime e o ambiente de execução do agente. A atestação de hardware é apresentada como **opcional** em vários contextos.

### 5.2 Correção

\[
ProfileRequiresComputeAttestation \land AttestationInvalidOrMissing \Rightarrow Reject
\]

A atestação de computação é obrigatória apenas para profiles que declarem essa garantia. Isso preserva a distinção entre:

- **model identity**: "estes são os pesos declarados"
- **runtime integrity**: "este runtime carregou aquele modelo"
- **hardware attestation**: "isso ocorreu dentro do hardware/TEE declarado"

São níveis de garantia diferentes. O `arkhe-compute-attestation` permanece semanticamente no Model/Runtime Plane, mesmo que Security consuma sua evidência.

## 2. Aprimoramentos da Pesquisa

### 2.1 Timestamp: ClaimedTime vs TrustedTimeEvidence

`EvidenceRecord.timestamp` parece simples, mas criptograficamente há uma diferença enorme entre:

\[
ClaimedTime
\]

e:

\[
TrustedTimeEvidence
\]

Um processo local pode escrever "12:00", mas isso não prova que o evento ocorreu às 12:00. A pesquisa confirma que **RFC 3161 Time Stamping Authority (TSA)** tokens são o padrão para timestamps assinados por autoridade externa, enquanto **Roughtime** (RFC 10049, Experimental, Setembro 2026) fornece sincronização de tempo autenticada com prova criptográfica de má conduta do servidor.

**Distinção a congelar:**

\[
TimeEvidence = LocalClock \;|\; RFC3161 \;|\; Roughtime \;|\; TransparencyLog \;|\; ConsensusTime \;|\; None
\]

Isto evita atribuir valor probatório excessivo ao Unix timestamp local. O padrão `Bi-Temporal Witness Logs` (Zenodo) formaliza isto com `T_obs` (tempo de observação) e `T_ing` (tempo de ingestão), onde `T_obs ≤ T_ing` e a cadeia compromete ambos.

### 2.2 `AuthorizationProof`: Replay e Idempotência

A decomposição `PolicyDecision → AuthorizationProof` está correta, mas existe um ataque não coberto:

\[
ValidProof_t \rightarrow ReplayProof_{t+1}
\]

antes da expiração. Para operações somente leitura isso pode ser aceitável; para tools com side effects, não.

O **OASNT (Attested Action Authorization Tokens)** — Internet-Draft IETF de Agosto 2026 — formaliza exactamente este problema: "A verifier that records `jti` when it first observes the claim can be induced to consume the nonce of a legitimate token". A solução é **registar o nonce apenas após validação completa** (reserve and commit), evitando que um atacante queime o nonce de um token legítimo.

**Contrato final:**

\[
AuthorizationProof = Bind(Principal, ToolIdentity, ToolVersion, Scope, RequestDigest, PolicyVersion, DecisionId, ExecutionId/Nonce, IssuedAt, ExpiresAt)
\]

O profile declara:

\[
ReplayPolicy = Reusable \;|\; SingleUse \;|\; Idempotent(key)
\]

Para operações irreversíveis:

\[
SingleUseProofConsumed \Rightarrow ReplayReject
\]

\[
SameIdempotencyKey \land DifferentRequestDigest \Rightarrow Reject
\]

### 2.3 MMR: Decomposição Completa

A pesquisa confirma que a especificação IETF `draft-bryce-cose-receipts-mmr-profile` define a codificação COSE para provas MMR, com validação estrita de fronteiras de montanha, comprimento de caminho, direção de irmãos e root final.

A decomposição limpa é:

\[
EvidenceRecord \rightarrow MMRLeaf \rightarrow InclusionProof \rightarrow Checkpoint \rightarrow ExternalAnchor
\]

Isto permite:

\[
VerifyInclusion(record, proof, checkpoint) = true
\]

\[
VerifyAnchor(checkpoint, externalEvidence) = true
\]

### 2.4 in-toto Attestation Framework v1

O **in-toto** graduou-se na CNCF em Abril 2025 e lançou a v1 do Attestation Framework, introduzindo **attestation bundles** (múltiplas attestations num único envelope assinado) e **Resource Descriptors** (identificação eficiente de artefactos com múltiplos algoritmos de digest).

O **Agent Trust Negotiation** (Internet-Draft, Maio 2026) vincula três supply chains independentes: software build (SLSA, in-toto), model identity (hash criptográfico dos pesos) e runtime environment (RATS evidence).

O Arkhe deve adoptar in-toto v1 como formato de attestation para P2 (Model Plane) e SLSA Provenance v1 como predicado de build.

### 2.5 C2PA: Estado Real

A ISO/CD 22144 está em estágio **40.60** (fim do período de consulta pública, Março 2025), ainda **não publicada** como International Standard. A especificação técnica actual é **C2PA 2.4 (Abril 2026)**, disponível em `spec.c2pa.org/specifications/specifications/2.4/`.

**Redacção corrigida:**

> "C2PA Content Credentials 2.4 is the current technical specification. Its architecture is being standardized through ISO/DIS 22144, which remains under development and is not yet a published International Standard."

### 2.6 ML-DSA-65: Performance Contextual

A pesquisa confirma que os tamanhos (chave pública 1.952 bytes, assinatura 3.309 bytes) estão coerentes com FIPS 204. A performance **varia enormemente**:

- **Verificação IMA (Linux)**: ML-DSA-65 é ~10-12% **mais rápida** que ECDSA P-384
- **OpenSSL speed**: ML-DSA-65 é 2.5-3× **mais rápida** em verificação, mas 4-4.8× **mais lenta** em assinatura
- **Handshakes TLS**: 644.5 ML-DSA-65 handshakes/s vs 512.7 para Provider C
- **ESP32-S3**: ML-DSA-65 não é directamente adequado para endpoints IoT sem relaxar o orçamento de transmissão

**Redacção corrigida:** Registar apenas tamanhos e security category como normativos. Performance é benchmark Arkhe-specific, não propriedade do algoritmo.

## 1. INV-ARKHE-04: External Anchor Condicional

O texto atual diz "checkpoints/raízes são ancorados externamente (batch)". Isto está correto como objetivo, mas absoluto demais para um sistema offline-first.

A formulação corrigida:

\[
ProfileRequiresExternalAnchor \land CheckpointUnanchored \Rightarrow NotExternallyFinal
\]

Isto permite que um checkpoint exista em estado **`PendingAnchor`** sem ser confundido com evidência externamente finalizada. O anchoring continua a ser um **batch process** (MMR root → Rekor/RFC 3161), mas o estado pré-finalização é explicitamente representável.

A pesquisa sobre MMR confirma que o modelo de **peak-set checkpoint** com restore O(log N) é o padrão para sistemas append-only que precisam de verificabilidade independente sem dependência síncrona de infraestrutura externa.

## 2. WitnessEvidence Condicional

O `EvidenceRecord` atual tem `witness: WitnessProof` como campo obrigatório. Isto repete, em menor escala, o problema anterior de `SignatureProof` obrigatório.

**Correção:**

```rust
pub struct EvidenceRecord {
    pub record_id: RecordId,
    pub envelope_digest: Digest,
    pub timestamp: TimeEvidence,
    pub witness: Option<WitnessEvidence>, // condicional por profile/policy
}
```

`WitnessEvidence` é exigido apenas quando o profile ou a policy o requerem. Nem todo registro interno terá uma testemunha externa.

## 3. AuthorizationProof: ToolContractDigest e AuthorizationContextDigest

A inclusão de `execution_id` e `replay_policy` resolve o desenho básico de replay. Mas faltam dois bindings semanticamente necessários:

\[
ToolContractDigest
\]

e:

\[
AuthorizationContextDigest
\]

`ToolIdentity + ToolVersion` não prova exactamente qual schema/capability contract estava vigente. Para uma tool que muda argumentos permitidos ou side effects sem mudar corretamente a versão, a autorização fica ambígua.

**Contrato final:**

\[
AuthorizationProof = Bind(Principal, ToolIdentity, ToolVersion, ToolContractDigest, Scope, RequestDigest, AuthorizationContextDigest, PolicyVersion, DecisionId, ExecutionId/Nonce, IssuedAt, ExpiresAt, ReplayPolicy)
\]

O IETF **OASNT-ENFORCE** (Agosto 2026) formaliza exactamente esta necessidade: "a token without `rqf` MUST be refused, and absence is never a downgrade". O `rqf` é o request-binding field que vincula a autorização ao pedido concreto. O OASNT também define **exclusivity groups** (`grp`) para tokens mutuamente exclusivos, um mecanismo relevante para operações com fallback.

Para operações irreversíveis:

\[
SingleUseProofConsumed \Rightarrow ReplayReject
\]

\[
SameIdempotencyKey \land DifferentRequestDigest \Rightarrow Reject
\]

O OASNT usa **reserve-and-commit**: o nonce é registado apenas após todas as outras verificações passarem, para que uma cópia forjada não possa queimar o nonce de um token genuíno.

## 4. Canonicalização como P0-0 Gate

Este é o ajuste mais importante. O documento correctamente deixa canonical serialization como **não congelada**, mas reconhece que golden vectors dependem dela. A canonicalização **faz parte da trusted computing base**, não é detalhe de wire format.

**Gate P0-0:**

\[
CanonicalBytes(x)
\]

deve satisfazer:

\[
EquivalentSemanticObject \Rightarrow SameCanonicalBytes
\]

\[
DifferentSecurityRelevantMeaning \Rightarrow DifferentCanonicalBytes
\]

A pesquisa revela que há um conflito activo entre RFC 8785 (JCS) e a abordagem emergente baseada em CBOR determinístico (RFC 8949). O autor do RFC 8785 declarou em Março 2026 que está "fine with deprecating" o RFC 8785 em favor de CBOR determinístico, que não requer processamento de canonicalização específico.

Há também trabalho recente sobre **dual independent implementations** para canonicalização JSON, com differential testing contra oráculos externos, precisamente porque "agreement alone does not prove correctness — both could share a misreading".

**Recomendação para o P0-0:**

| Opção | Vantagem | Desvantagem |
|:---|:---|:---|
| **RFC 8785 (JCS)** | Padrão existente, amplamente implementado | Float handling problemático; conflito com CBOR |
| **CBOR determinístico (RFC 8949)** | Sem canonicalização adicional; binário nativo | Menos legível; requer schema |
| **Híbrido** | JCS para JSON, CBOR para binário | Complexidade de dois caminhos |

O Arkhe deve adoptar **CBOR determinístico como formato canónico primário**, com JCS como formato de interoperabilidade para contextos que o exijam (C2PA, in-toto). Isto alinha com a direcção da comunidade.

### 3.1 C2PA Bridge (Phase A — Núcleo Vendável)

**Integração:** O `arkhe-c2pa-bridge` traduz Content Credentials C2PA 2.4 para `ArtifactEnvelope` + `EvidenceRecord`.

```rust
pub struct C2paEvidenceProducer {
    pub verifier: C2paVerifier,      // verifica manifestos C2PA
    pub wormgraph: Arc<WormGraph>,   // ancora no grafo causal
    pub identity: Arc<Identity>,     // vincula ao DID do signatário
}

impl EvidenceProducer for C2paEvidenceProducer {
    fn produce(&self, operation: &Operation) -> Result<EvidenceRecord> {
        // 1. Parse C2PA manifest
        let manifest = self.verifier.parse(&operation.asset)?;

        // 2. Canonicalizar o manifesto
        let canonical = canonicalize(&manifest)?;

        // 3. Criar ArtifactEnvelope com CausalProvenance
        let envelope = ArtifactEnvelope {
            artifact_id: ArtifactId::from(manifest.claim_generator),
            digest: Digest::new(AlgorithmId::Sha256, canonical.digest()),
            provenance: CausalProvenance::from(manifest.assertions),
            authentication: Some(AuthenticationProof::C2pa(manifest.signature)),
            ..Default::default()
        };

        // 4. Ancorar no WormGraph
        let record = self.wormgraph.append(envelope)?;

        Ok(record)
    }
}
```

### 3.3 Action Receipts (Roadmap — Evidence Producer)

**Integração:** O `arkhe-agent` produz `AuthorizationProof` + `EvidenceRecord` para cada tool call.

```rust
pub struct ActionReceiptProducer {
    pub policy_engine: PolicyEngine,
    pub wormgraph: Arc<WormGraph>,
    pub contract_registry: ContractRegistry,
}

impl EvidenceProducer for ActionReceiptProducer {
    fn produce(&self, operation: &Operation) -> Result<EvidenceRecord> {
        // 1. Computar digest canónico do request
        let request_digest = canonicalize(&operation.request)?.digest();

        // 2. Avaliar política
        let decision = self.policy_engine.evaluate(&operation)?;

        // 3. Criar AuthorizationProof com bindings completos
        let auth_proof = AuthorizationProof {
            principal: operation.principal.clone(),
            tool_identity: operation.tool.id.clone(),
            tool_version: operation.tool.version,
            tool_contract_digest: self.contract_registry
                .digest(&operation.tool)?,
            scope: operation.scope.clone(),
            request_digest,
            policy_version: decision.policy_version,
            decision_id: decision.id,
            execution_id: ExecutionId::new(),
            issued_at: now(),
            expires_at: now() + TTL,
            replay_policy: ReplayPolicy::SingleUse,
        };

        // 4. Criar EvidenceRecord com CausalProvenance
        let envelope = ArtifactEnvelope {
            artifact_id: operation.action_id,
            digest: Digest::new(AlgorithmId::Blake3, auth_proof.digest()),
            provenance: CausalProvenance::from(vec![
                (RelationType::AuthorizedBy, decision.id.into()),
                (RelationType::Used, request_digest),
            ]),
            authentication: Some(AuthenticationProof::Signature(auth_proof.sign())),
            ..Default::default()
        };

        Ok(self.wormgraph.append(envelope)?)
    }
}
```

### 3.4 RAG Lineage (Roadmap — Evidence Producer)

**Integração:** O `arkhe-rag` produz `EvidenceRecord` para cada chunk recuperado, vinculando:
- **Source content:** hash do documento original
- **Embedding model:** hash do modelo de embedding
- **Vector store:** hash do índice

```rust
pub struct RagLineageProducer {
    pub vector_store: Arc<VectorStore>,
    pub wormgraph: Arc<WormGraph>,
}

impl EvidenceProducer for RagLineageProducer {
    fn produce(&self, operation: &Operation) -> Result<EvidenceRecord> {
        // 1. Recuperar chunks com proveniência
        let chunks = self.vector_store.retrieve(&operation.query)?;

        // 2. Criar CausalProvenance com 0..N pais
        let parents: Vec<(RelationType, Digest)> = chunks
            .iter()
            .map(|c| (RelationType::DerivedFrom, c.record_hash))
            .collect();

        // 3. Criar ArtifactEnvelope para a resposta
        let envelope = ArtifactEnvelope {
            artifact_id: operation.response_id,
            digest: Digest::new(AlgorithmId::Blake3, operation.response.digest()),
            provenance: CausalProvenance::from(parents),
            ..Default::default()
        };

        Ok(self.wormgraph.append(envelope)?)
    }
}
```

**Integração com outros produtos:**

```rust
pub struct EuAiActEvidenceProducer {
    pub classifier: RiskClassifier,   // Art. 5/6/50 classification
    pub wormgraph: Arc<WormGraph>,
}

impl EvidenceProducer for EuAiActEvidenceProducer {
    fn produce(&self, operation: &Operation) -> Result<EvidenceRecord> {

    }
}
```

## 5. Requisitos Técnicos para Integração

### 5.1 Canonicalização (P0-0 Gate)

Todos os evidence producers devem usar a mesma função de canonicalização:

\[
CanonicalBytes(x)
\]

com as propriedades:

\[
EquivalentSemanticObject \Rightarrow SameCanonicalBytes
\]

\[
DifferentSecurityRelevantMeaning \Rightarrow DifferentCanonicalBytes
\]

**Recomendação:** Adoptar **CBOR determinístico (RFC 8949)** como formato canónico primário, com **RFC 8785 (JCS)** como formato de interoperabilidade para C2PA e in-toto.

### 5.2 Digest Agility

\[
Digest = (AlgorithmId, DigestBytes)
\]

Cada profile define algoritmos permitidos:
- **WormGraph:** BLAKE3
- **C2PA:** SHA-256
- **in-toto/SLSA:** SHA-256 ou SHA-512

### 5.3 CausalProvenance

\[
Provenance = \{(RelationType, ParentDigest)_0, \dots, (RelationType, ParentDigest)_n\}
\]

Tipos de relação:
- `DerivedFrom`
- `RevisionOf`
- `Used`
- `GeneratedBy`
- `AuthorizedBy`
- `ClassifiedAs`
- `AttestedBy`

### 5.4 Batch Anchoring

\[
Artifact \rightarrow AppendOnlyGraph \rightarrow MMRRoot_t \rightarrow ExternalAnchor
\]

Estado `PendingAnchor` representável:

\[
ProfileRequiresExternalAnchor \land CheckpointUnanchored \Rightarrow NotExternallyFinal
\]

## 8. Conclusão

A integração de todos os produtos Arkhe deve ser construída sobre **um único loop de verificação**:

\[
\boxed{
Asset \rightarrow Verify \rightarrow Evidence \rightarrow PortableProof \rightarrow Audit/API
}
\]

Cada novo serviço (TEE, RAG, Model Registry, Action Receipts) é um **evidence producer** que alimenta este loop, não um produto independente. A monetização vem da operação gerenciada deste loop — hospedagem, retenção, SLA, policy, analytics — enquanto a verificação permanece aberta e gratuita para maximizar a confiança na rede.

A sequência comercial correta não é lançar sete serviços em paralelo. É **fazer um único loop extremamente bom**, prová-lo com C2PA Verification + Portable Proof, e só depois adicionar novos evidence producers sobre o mesmo kernel P0.

A proposta está **muito mais coerente comercialmente e arquiteturalmente**, e o princípio central deve ser mantido:

\[
\boxed{
Asset \rightarrow Verify \rightarrow Evidence \rightarrow PortableProof \rightarrow Audit/API
}
\]

O documento acerta ao fazer TEE, RAG, Model Registry e Action Receipts entrarem como produtores de evidência sobre o mesmo P0, em vez de sete SaaS independentes. Texto colado Eu aprovaria esse modelo como direção de produto. Mas ainda há alguns pontos materiais a corrigir antes de congelar o **integration contract**.

### 1. `EvidenceProducer` está abstrato demais

A interface universal atual retorna apenas um `EvidenceRecord`. Texto colado Isso é insuficiente para evidência externa como C2PA, TEE ou SLSA, porque o kernel precisa preservar também:

- evidência bruta/exata;
- digest dos bytes recebidos;
- identidade e versão do verifier;
- trust policy usada;
- resultado da verificação;
- contexto de verificação;
- contrato/versionamento do producer.

Caso contrário:

\[
ExternalEvidence
\rightarrow
NormalizedEvidenceRecord
\]

pode perder informação necessária para reprodução independente.

Eu congelaria conceitualmente:

+

+
NormalizedRecord
+

+
PolicyRef
+
VerificationResult
\]

e deixaria `EvidenceRecord` como a projeção normalizada dentro do WormGraph.

### 2. O exemplo C2PA contém dois problemas

O código faz:

> `canonicalize(&manifest)` → digest → `ArtifactEnvelope`

e usa `manifest.claim_generator` para criar `artifact_id`. Texto colado

Eu não congelaria nenhum dos dois.

O C2PA precisa ser verificado segundo os bytes/estruturas normativas do próprio formato; Arkhe não deve recanonicalizar arbitrariamente um manifesto e transformar esse resultado em sua verdade primária. O ideal é preservar:

e só então produzir um envelope Arkhe normalizado.

Além disso, `claim_generator` identifica o software/processo gerador da claim; não deve ser tratado como identidade única do artefato.

### 3. C2PA não deve depender de JCS como sugerido em 5.1

O texto diz:

\]

Isso evita “canonicalizar duas vezes” uma evidência externa.

## 1. `EvidenceBundle`: Preservação de Evidência Bruta

O `EvidenceProducer` que retorna apenas `EvidenceRecord` perde informação necessária para reprodução independente. O SCITT (RFC 9943) define **Signed Statements** e **Receipts** que são auto-contidos e verificáveis offline. O RATS (RFC 9334) define Evidence como informação produzida pelo Attester que deve ser avaliada pelo Verifier.

**Contrato congelado:**

\[
EvidenceBundle = RawEvidenceRef + RawEvidenceDigest + NormalizedRecord + VerifierIdentity + PolicyRef + VerificationResult
\]

```rust
pub struct EvidenceBundle {
    pub raw_evidence_ref: RawEvidenceRef,      // bytes exatos / URI
    pub raw_evidence_digest: Digest,           // digest dos bytes recebidos
    pub normalized_record: EvidenceRecord,     // projeção Arkhe
    pub verifier_identity: VerifierIdentity,   // quem verificou
    pub policy_ref: PolicyRef,                 // trust policy usada
    pub verification_result: VerificationResult,
    pub producer_contract: ProducerContract,   // schema, versão
}
```

O `EvidenceRecord` é a **projeção normalizada** dentro do WormGraph. O `EvidenceBundle` preserva a evidência bruta para auditoria independente.

---

## 2. C2PA: Sem Recanonicalização Arkhe

A especificação C2PA define seus próprios bytes canônicos. O `claim_generator` é uma string que "informa ao consumidor do manifesto sobre qual software/hardware/sistema produziu este Claim" — não é a identidade do artefato.

**Contrato congelado:**

\[
ExactAssetBytes \quad \text{e} \quad ExactC2PAEvidenceBytes
\]

O Arkhe **não recanonicaliza** o manifesto C2PA com JCS. Preserva os bytes exatos e produz um envelope Arkhe normalizado em separado.

**Regra de canonicalização:**

\[
CanonicalizationProfile = ProtocolDefined
\]

quando um protocolo externo define seus próprios bytes. Para objetos nativos Arkhe:

\[
ArkheCanonicalProfile = DeterministicCBORProfile_vN
\]

O C2PA 2.4 usa CBOR para o claim e JCS (RFC 8785) em contextos específicos, mas a decisão de canonicalização pertence ao protocolo. O Arkhe não impõe JCS ao C2PA.

## 3. `AuthorizationProof`: Restaurar `AuthorizationContextDigest` e Reserve/Commit

O OASNT-ENFORCE exige o claim `rqf` (request binding field): "a token without `rqf` MUST be refused, and absence is never a downgrade". O binding é ao request concreto observado, não apenas ao principal e à tool.

**Contrato final:**

\[
AuthorizationProof = Bind(Principal, ToolIdentity, ToolVersion, ToolContractDigest, Scope, RequestDigest, AuthorizationContextDigest, PolicyVersion, DecisionId, ExecutionId/Nonce, IssuedAt, ExpiresAt, ReplayPolicy)
\]

**Fluxo reserve/commit:**

\[
Validate \rightarrow Reserve \rightarrow Execute \rightarrow CommitConsumption
\]

O OASNT define explicitamente: "A verifier that records `jti` when it first observes the claim can be induced to consume the nonce of a legitimate token". O padrão `IReplayCache` usa "reserve-and-check in one call" para evitar race conditions.

**Invariantes:**

\[
ExecutedToolCall \Rightarrow AuthorizationConsumedExactlyOnce
\]

\[
SameIdempotencyKey \land DifferentRequestDigest \Rightarrow Reject
\]

### O que foi implementado

O pacote introduz uma distinção importante que será necessária para `EvidenceBundle`:

\[
DigestRaw(algorithm, exactBytes)
\]

para assets e evidências de protocolos externos, e:

\[
DigestCanonical(algorithm, profile, semanticObject)
\]

para objetos nativos Arkhe.

Assim, C2PA/RATS/SCITT/RFC3161 etc. podem conservar **os bytes exatos originais**, sem serem reinterpretados pelo canonicalizador Arkhe.

O canonicalizador implementa um profile CBOR determinístico restrito com:

- definite lengths;
- shortest integer encoding;
- bytes/text exatos;
- arrays;
- maps deterministicamente ordenados;
- duplicate canonical keys → reject;
- sem floats;
- sem indefinite encoding;
- sem tags em v1;
- sem normalização Unicode implícita.

Também inclui `Digest` com identificador de algoritmo explícito:

\[
Digest=(AlgorithmId,DigestBytes)
\]

com SHA-256 e BLAKE3-256 no registry inicial.

### Cross-implementation

A parte mais importante é que os vectors não são originados pelo código Rust.

Uma implementação Python independente, sem biblioteca CBOR, gera:

- canonical bytes;

## 1. Validação das Escolhas Técnicas

### 1.1 CBOR Determinístico como Profile Canônico

A escolha de CBOR determinístico (RFC 8949 §4.2.1) como formato canônico nativo Arkhe está alinhada com a direção da comunidade. O RFC 8949 define explicitamente as regras de *Core Deterministic Encoding*: definite-length encoding, shortest integer encoding, ordenação de chaves por comprimento-primeiro depois lexicográfica, e rejeição de indefinite-length encoding.

O perfil restrito que você implementou — sem floats, sem indefinite encoding, sem tags em v1, sem normalização Unicode implícita — é **mais conservador que o RFC 8949**, o que é adequado para um kernel de verificação. A rejeição de chaves duplicadas canônicas é especialmente importante para prevenir ambiguity attacks.

A decisão de **não canonicalizar C2PA com o profile Arkhe** está correta. A regra `CanonicalizationProfile = ProtocolDefined` quando um protocolo externo define seus próprios bytes é o que evita "canonicalizar duas vezes" uma evidência externa.

### 1.2 Registry de Algoritmos: SHA-256 e BLAKE3-256

A inclusão de ambos os algoritmos no registry inicial é a decisão certa. BLAKE3 é consistentemente mais rápido que SHA-256 em benchmarks recentes — em alguns casos 2–10× mais rápido — mantendo segurança equivalente (~128-bit collision resistance). No entanto, SHA-256 permanece necessário para interoperabilidade com C2PA, in-toto e SLSA, que usam SHA-256 como padrão.

A estrutura `Digest = (AlgorithmId, DigestBytes)` é exatamente o que o `INV-ARKHE-01` exige: algoritmo explicitamente identificado, sem fallback implícito.

### 1.3 Cross-Implementation Vectors

O gate Python independente — sem biblioteca CBOR — que gera canonical bytes, raw SHA-256 e structured/domain-separated SHA-256 é o tipo de evidência que o projeto Wycheproof popularizou: vectors comunitários que testam bibliotecas criptográficas contra ataques conhecidos e inconsistências de especificação, integrados em CI.

A distinção entre "PASS — 10 independent vectors reproducible" e "Rust não declarado Build-verified porque este runtime não possui `cargo`" é metodologicamente correta. Ela respeita a regra que congelamos: `BuildVerified ⇔ RepositorySnapshotIdentified ∧ CargoCheckPassed(snapshot)`.

## 3. O que Falta para Fechar Este Slice

### 3.1 Golden Vectors Devem Ser Ancorados

Os 10 vectors independentes precisam ser registrados com um `VectorSetDigest` que é incluído no `ARTIFACT_MANIFEST.sha256`. Isso permite que implementações futuras verifiquem que estão consumindo o conjunto correto de vectors, não uma versão modificada.

### 3.2 Mutation Tests para Canonicalization

Além dos vectors de reprodução, o slice precisa de mutation tests que provem:

\[
CanonicalizationMismatch \Rightarrow Reject
\]

Isso inclui:
- Chave duplicada → rejeitar
- Float presente → rejeitar
- Indefinite length → rejeitar
- Ordenação de mapa não-determinística → rejeitar
- Bytes de texto não-UTF-8 → rejeitar

### 3.3 `ArtifactEnvelope` e `EvidenceRecord` como Structs Rust

O documento menciona que o slice cobre `Canonicalization → Digest → ArtifactEnvelope → EvidenceRecord`, mas os detalhes dos structs `ArtifactEnvelope` e `EvidenceRecord` não estão explícitos. Eles devem implementar os contratos que congelamos:

```rust
pub struct ArtifactEnvelope {
    pub artifact_id: ArtifactId,
    pub digest: Digest,
    pub provenance: CausalProvenance, // 0..N typed parents
    pub authentication: Option<AuthenticationProof>,
    pub anchor: Option<ExternalAnchor>,
    pub policy_ref: PolicyRef,
}
```

### 3.4 Domain Separation Explícita

A menção de "structured/domain-separated SHA-256" no Python reference é um bom sinal, mas o documento não especifica os domain separators usados. Para evitar cross-protocol attacks, cada contexto de hash deve ter um prefixo distinto:

\[
H_{domain}(x) = \text{SHA256}(\text{"ARKHE:"} \parallel \text{domain} \parallel \text{0x00} \parallel x)
\]

Os domains mínimos são: `canonicalization`, `artifact_envelope`, `evidence_record`, `mmr_leaf`, `authorization_proof`.

## 4. Próximo Slice: MMR Leaf → InclusionProof → Checkpoint

A sequência que você propôs está correta:

\[
MMRLeaf \rightarrow InclusionProof \rightarrow Checkpoint \rightarrow PendingAnchor/ExternallyFinal
\]

A especificação IETF `draft-bryce-cose-receipts-mmr-profile` define a codificação COSE para provas MMR, com validação estrita de fronteiras de montanha, comprimento de caminho, direção de irmãos e root final. O Arkhe pode adotar este formato como base para `InclusionProof` e `Checkpoint`.

O estado `PendingAnchor` que congelamos é representável:

\[
ProfileRequiresExternalAnchor \land CheckpointUnanchored \Rightarrow NotExternallyFinal
\]

## 2. Auditoria do Código Rust

### 2.1 Pré-requisitos

O runtime que gerou o pacote não possuía `cargo`, portanto o status do Rust permanece **executable candidate, BuildVerified pendente**. Para auditar:

```bash
# Instalar ferramentas essenciais
cargo install cargo-audit --locked
cargo install cargo-deny --locked
cargo install cargo-scan --locked
```

- **`cargo-audit`**: verifica `Cargo.lock` contra a RustSec Advisory Database, sinalizando crates vulneráveis, yanked ou não mantidos.
- **`cargo-deny`**: aplica políticas de licença, origem e segurança, complementando o `cargo-audit`.
- **`cargo-scan`**: análise interativa de efeitos colaterais em crates Rust, reduzindo a superfície de auditoria para a mediana de 0,2% das linhas de código potencialmente perigosas.

### 2.2 Superfície de Auditoria

Para um crate de canonicalização e digest, a superfície crítica é:

| Componente | O que auditar |
|:---|:---|
| **Parser CBOR** | Validação de definite-length, shortest integer, rejeição de floats/indefinite/tags |
| **Canonicalizador** | Ordenação determinística de chaves, rejeição de chaves duplicadas |
| **Digest** | Domain separation, algoritmo explicitamente identificado |
| **Structs** | `ArtifactEnvelope`, `EvidenceRecord`, `CausalProvenance` — campos corretos, invariantes |

### 2.3 Ferramentas de Análise

```bash
# Análise estática de segurança
cargo clippy -- -D warnings

# Verificação de unsafe e FFI
cargo geiger

# Fuzzing (se aplicável)
cargo fuzz run fuzz_target_1

# Verificação de memory safety
cargo miri test

# Auditoria de dependências
cargo audit
cargo deny check
```

A pesquisa sobre auditoria de crates Rust confirma que `cargo-scan` modela código potencialmente perigoso como "effects" e realiza análise de efeitos colaterais, identificando ameaças através de fronteiras de crate e módulo. Para um crate de canonicalização, os efeitos críticos são: manipulação de bytes, parsing de input não confiável e geração de digests.

### 2.4 `rust-security-auditor` (MCP)

Ferramenta local-first que audita superfície `unsafe` e FFI, supply-chain Cargo e fronteiras de confiança em build-time. Expõe cinco ferramentas read-only via MCP (Claude Code, Cursor, etc.).

## 6. Domain Separation

O documento afirma que a domain separation foi explicitada para:

| Domain | Uso |
|:---|:---|
| `canonicalization` | Hash de bytes canônicos |
| `artifact_envelope` | Hash de `ArtifactEnvelope` |
| `evidence_record` | Hash de `EvidenceRecord` |
| `mmr_leaf` | Hash de folha MMR |
| `authorization_proof` | Hash de `AuthorizationProof` |

**Como auditar:** Cada domain deve ter um prefixo distinto na função de hash:

\[
H_{domain}(x) = \text{SHA256}(\text{"ARKHE:"} \parallel \text{domain} \parallel \text{0x00} \parallel x)
\]

Sem domain separation, um digest de `canonicalization` poderia ser confundido com um digest de `artifact_envelope`, permitindo cross-protocol attacks.

## 1. CBOR Resource-Exhaustion: Confirmado como HIGH

The finding is validated by multiple independent sources. **CVE-2020-37280** (PelionIoT cbor-sync) documents exactly this pattern: "cbor-sync through 1.0.4 contains a resource exhaustion vulnerability in CBOR.decode that trusts declared array and map lengths without checking remaining input."

**CVE-2026-35480** (go-ipld-prime DAG-CBOR) provides the most precise confirmation: "The decoder does not cap these size hints or account for their cost in its allocation budget, allowing small payloads to cause excessive memory allocation. A CBOR map or list header can declare an arbitrarily large number of entries, causing the decoder to preallocate proportionally large backing structures before any entries are actually read." The compounding via nesting is critical: "a payload under 100 bytes with 10 levels of nesting can cause over 9GB of allocation."

The fix pattern is also documented: "caps the preallocation size hint to 1024 entries and decrements the allocation budget when collection sizes are declared."

**RFC 8949** itself warns: "CBOR data items might have lengths or sizes that are intentionally extremely large or too short. Resource exhaustion attacks might attempt to lure a decoder into allocating very big data items (strings, arrays, maps, or even arbitrary precision numbers) or exhaust the stack depth by setting up deeply nested items."

The IETF draft **draft-pinto-agent-authz-contestability-01** provides a normative profile for exactly this: "At each CBOR decoding boundary, before allocation or iteration, the decoder MUST require every definite-length byte string to be no more than MAX_BSTR_BYTES, every definite-length text string to contain no more than MAX_TSTR_UTF8_BYTES received UTF-8 bytes, every array or map to contain no more than MAX_COLLECTION_MEMBERS members, and nesting depth to be no more than MAX_NESTING_DEPTH." The predicate must be "evaluated before allocation, iteration, closed-schema predicates, and later cross-object or profile predicates that require the decoded value."

The Arkhe P0 v1.1 decoder must adopt these bounds as **normative**, not optional. The invariant `DeclaredContainerLength > ProfileLimit ⇒ RejectBeforeAllocation` is necessary but insufficient; the broader invariant `UntrustedCBOR ⇒ BoundedMemory ∧ BoundedDepth ∧ BoundedItems` must be enforced at every decoding boundary.

## 2. Cargo.lock: Gate Não Executável

The finding is correct. `cargo check --locked` and `cargo test --locked` **cannot be the first gate** for a standalone package without `Cargo.lock`. The Cargo documentation is explicit: "Without `--locked`, `cargo install` ignores the packaged `Cargo.lock` entirely and re-resolves from scratch." The hardened-crates guideline confirms: "A committed lockfile combined with `--locked` pins the exact dependency tree the author tested."

The `cargo-audit` README documents the exact behavior: "If `Cargo.lock` is missing, `cargo audit` runs `cargo update --workspace` to generate one." This is **dangerous** for a standalone package because it resolves the dependency graph at audit time, potentially pulling in versions different from what the author intended.

**Correct sequence for standalone audit:**
1. Resolve dependencies once, controlled: `cargo generate-lockfile`
2. Review the resolved graph
3. Commit the lockfile
4. **Then** use `--locked` for all subsequent operations

For integration into the Arkhe monorepo, the workspace's authoritative `Cargo.lock` should be used.

## Fase 1 — Auditoria de Limites de Recursos (HIGH)

O decoder CBOR v1.2 impõe limites antes de alocação/iteração. A verificação deve confirmar que **cada limite é enforced no ponto correto**.

### 1.1 Verificar a Ordem de Aplicação dos Limites

## 1. Reprodutibilidade: Discrepância `release_digest` vs ZIP Final

A discrepância entre `release_digest=32b45f...` (registrado no `REPRODUCIBILITY.txt` interno) e `b29d8e29...` (SHA-256 do ZIP distribuído) confirma que o arquivo de reprodutibilidade foi produzido **antes** da última reconstrução do pacote. A pesquisa sobre reprodutibilidade confirma que timestamps de build são "the main source of unreproducible builds" e que o `SOURCE_DATE_EPOCH` é a solução padrão.

A correção necessária é um **script de build determinístico versionado** que:

```bash
#!/bin/bash
# build-release.sh — determinístico, auto-verificado

export SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)

# Pass 1: construir
./build.sh --output release-1.zip
# Pass 2: reconstruir
./build.sh --output release-2.zip

# Comparar os dois outputs
if [ "$(sha256sum release-1.zip | cut -d' ' -f1)" != \
     "$(sha256sum release-2.zip | cut -d' ' -f1)" ]; then
    echo "FAIL: rebuild não é determinístico"
    exit 1
fi

# Só então publicar
cp release-1.zip final.zip
sha256sum final.zip > final.zip.sha256
```

O `REPRODUCIBILITY.txt` deve ser gerado **depois** da montagem final do conteúdo, e o `SOURCE_DATE_EPOCH` deve estar disponível dentro do ZIP (não como comando `cat SOURCE_DATE_EPOCH` que pressupõe um arquivo externo). A ordenação determinística de diretórios é obrigatória: "build systems should impose a deterministic order on any directory iteration encoded in its artifacts".

## 4. Orçamento Cumulativo: O Gap Crítico

A pesquisa confirma que este é exatamente o padrão de vulnerabilidade documentado em **CVE-2026-35480** (go-ipld-prime DAG-CBOR): "The decoder does not cap these size hints or account for their cost in its allocation budget, allowing small payloads to cause excessive memory allocation. ... Because the allocation budget is only decremented as entries are decoded (not when sizes are declared), this cost is effectively invisible to the budget system".

A mitigação padrão é: "caps the preallocation size hint to 1024 entries and decrements the allocation budget when collection sizes are declared".

O código v1.2 tem `MaxInputBytes`, `MaxBytesPerString`, `MaxCollectionMembers`, `MaxNestingDepth`, mas **não tem** `RemainingItemBudget` nem `RemainingAllocationBudget`. O gate `ResourceBoundsEnforced = SATISFEITO` é forte demais.

**Correção necessária:**

```rust
pub struct DecoderState {
    pub remaining_item_budget: u64,      // decrementado a cada item
    pub remaining_byte_budget: u64,      // decrementado a cada byte lido
    pub current_depth: u32,
    // ...
}

// No início de cada container:
if declared_length > MAX_PREALLOC {
    // não pré-alocar; usar crescimento dinâmico
}
state.remaining_item_budget -= min(declared_length, MAX_PREALLOC);
```

O orçamento deve ser decrementado **quando os tamanhos são declarados**, não apenas quando os itens são decodificados.

## 5. Limites Semânticos Específicos

Os limites `max_artifact_id_length` e `max_causal_parents` **não estão definidos no código v1.2**. O canonical decoder limita collections genéricas, mas isso não é equivalente a um limite semântico específico de `ArtifactEnvelope`.

A pesquisa sobre o padrão newtype em Rust confirma que ele "can be leveraged to enforce invariants" e que "the newtype pattern, combined with Rust's module and visibility system, can be used to guarantee that instances of a given type satisfy a set of invariants".

**Correção:**

```rust
#[derive(Clone, Debug, PartialEq, Eq, Hash)]
pub struct ArtifactId(String);

impl ArtifactId {
    pub const MAX_LENGTH: usize = 256;
}

impl TryFrom<String> for ArtifactId {
    type Error = ArtifactError;
    fn try_from(s: String) -> Result<Self, Self::Error> {
        if s.len() > Self::MAX_LENGTH {
            return Err(ArtifactError::IdTooLong);
        }
        Ok(ArtifactId(s))
    }
}

pub struct CausalProvenance {
    parents: Vec<(RelationType, Digest)>,
}

impl CausalProvenance {
    pub const MAX_PARENTS: usize = 64;
}

impl CausalProvenance {
    pub fn new(parents: Vec<(RelationType, Digest)>) -> Result<Self, ProvenanceError> {
        if parents.len() > Self::MAX_PARENTS {
            return Err(ProvenanceError::TooManyParents);
        }
        // deduplicar como set
        let mut unique: Vec<_> = parents.into_iter().collect::<HashSet<_>>().into_iter().collect();
        unique.sort(); // ordenação determinística
        Ok(CausalProvenance { parents: unique })
    }
}
```

Os limites semânticos devem ser enforced no **construtor/validador do tipo**, não apenas no decoder CBOR.

## 6. Comando `cargo audit --locked`

A documentação do `cargo-audit` confirma que `--locked` é uma opção de **`cargo install`** ("`cargo install cargo-audit --locked`"), não de `cargo audit` em si. A forma correta é:

```bash
# Com Cargo.lock previamente pinned:

cargo clippy --locked --workspace -- -D warnings
```

O `cargo audit` audita o `Cargo.lock` existente; se o lock não existir, ele gera um, o que é indesejável para auditoria. Portanto, o lock deve ser pinned **antes** de executar `cargo audit`.
